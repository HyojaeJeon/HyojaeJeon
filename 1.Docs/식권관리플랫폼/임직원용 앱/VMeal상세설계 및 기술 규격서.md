## 1. 개요 및 핵심 가치

### 1.1 프로덕트 정의

VMeal은 **기업 임직원 전용 모바일 식권 앱**이다. CorporatePortal(기업 관리자 웹)에서 설정한 정책과 예산에 따라 임직원이 **플랫폼 제휴 가맹점 중 소속 기업이 등록/설정한 식당에서만** 앱 내 주문+결제 또는 RFID로 식대를 결제하고, 잔액/이용 내역을 실시간으로 확인하는 B2E(Business-to-Employee) 앱이다.

### 1.2 핵심 가치 정의

| 가치 | 설명 | 측정 지표 |
|------|------|----------|
| **3초 결제** | 앱 실행 → 결제 완료까지 3초 이내 | Cold start → 결제 화면 TTI ≤ 3s |
| **잔액 투명성** | 회사 지원금/개인 충전의 실시간 분리 표시 | 잔액 API 응답 ≤ 200ms (P95) |
| **정책 실시간 반영** | 시간/장소/금액 제한이 결제 시점에 즉시 적용 | 정책 변경 → 앱 반영 ≤ 5s |
| **가맹점 탐색** | GPS 기반 주변 제휴 식당 지도 + 필터 (**소속 기업이 등록한 식당만 노출**) | 지도 로드 TTI ≤ 2s, 마커 렌더 ≤ 60fps |
| **통합 원장** | 회사/개인 하이브리드 Split Payment | 단일 트랜잭션 내 2-bucket 차감 |

### 1.3 사용자 페르소나

| 페르소나 | 환경 | 핵심 니즈 |
|----------|------|----------|
| 도심 사무직 A | 오피스 주변 로컬 식당 | 빠른 앱 주문+결제, 다양한 가맹점 탐색 |
| 공장 교대근무 B | 산업단지 구내식당 | RFID 태그 0.8초 결제, 오프라인 가능 |
| 재택근무 C | 자택 주변 배달/포장 | 배달앱 연동, 개인 충전으로 차액 결제 |
| 외근/출장 D | 타 지역 제휴점 | 지오펜싱 확인, 지도 내비 연동 |

### 4.2 인증 방식

- **소셜 로그인 (기본)**:
  - 구글 (Google Sign-In)
  - 애플 (Apple Sign-In) — iOS 필수
  - 이메일 + 비밀번호
  - 휴대전화번호 OTP (Firebase SMS Gateway)
- **향후 확장**: 사번 + 암호 로그인 (기업 HRIS 연동 시)
- **세션 유지**: HttpOnly refresh token (쿠키) + 메모리 access token
- **생체 인증**: 앱 진입 시 Face ID / Touch ID / 지문 (react-native-biometrics)
- **Quick Order 진입**: 생체 인증으로 잠금 해제 → 즉시 주문 화면 (3초 원칙)

### 4.3 세션 관리 (CentralApi 연동)

| 항목 | 규격 |
|------|------|
| Access Token 저장 | 메모리 전용 (AsyncStorage 저장 금지) |
| Refresh Token 저장 | HttpOnly 쿠키 (서버 발급) |
| 세션 갱신 | 만료 2분 전 자동 silent refresh |
| 갱신 실패 | 30초 후 1회 재시도 → 실패 시 로그인 화면 |
| 인증 에러 코드 | `UNAUTHENTICATED`, `SESSION_REVOKED`, `REFRESH_SESSION_EXPIRED`, `ACCOUNT_INACTIVE` |

### 4.4 Identity Binding (기업 매핑)

1. 관리자가 CorporatePortal에서 임직원 생성 → `MealEmployee` 레코드 생성
2. 임직원에게 딥링크 전송 (`vmeal://invite/{companyCode}`)
3. 임직원이 딥링크 클릭 → 앱 설치/실행 → 회사 자동 매핑
4. 전화번호 OTP로 본인 확인 → `MealEmployee.phone`과 일치 검증
5. 인증 완료 → 앱 내 `corporateId`, `employeeId`, `walletId` 바인딩

### 5.2 OrderScreen (주문+결제) & RFID 결제

> **v2.0 변경**: QR/바코드 결제 화면은 폐기. 앱 내 직접 주문+결제로 전환. RFID 배지 결제는 POS에서 처리하며 앱은 결과 알림만 수신.

```

├──────────────────────────────────────┤
│                                      │
│  ─── 이용 방식 ─────────────────── │
│  [🍽️ 매장 식사]  [📦 포장]          │  ← 선택 (기본: 매장 식사)
│                                      │
│  ─── 메뉴 선택 ─────────────────── │
│  ┌────────────────────────────────┐  │
│  │ 🍜 쌀국수 (Phở Bò)     ₫65,000│  │
│  │    수량: [-] 1 [+]             │  │
│  │    옵션: 고기 추가 +₫15,000   │  │
│  └────────────────────────────────┘  │
│  ┌────────────────────────────────┐  │
│  │ 🥤 아이스 커피         ₫25,000│  │
│  │    수량: [-] 1 [+]             │  │
│  └────────────────────────────────┘  │
│                                      │
│  ─── 예정 방문 시간 ────────────── │
│  [11:30] [12:00] [12:30] [13:00]    │  ← 30분 슬롯 (매장 설정)
│  🪑 12:00 빈 테이블 8/20석           │  ← POS 연동 매장만 실시간 표시
│  ⏱️ 평균 식사 시간: 약 35분           │  ← POS 테이블 점유 데이터 기반
│  ⚠️ 12:30 피크타임 (잔여 3석)        │  ← 비연동 매장은 이 3줄 미표시
│                                      │
│  ─── 결제 요약 ─────────────────── │
│  총 금액                   ₫105,000 │
│  ├ 회사 지원금 차감        ₫100,000 │
│  └ 개인 충전 차감           ₫5,000  │
│                                      │
│        ┌──────────────────┐          │
│        │ ₫105,000 주문·결제하기│       │  ← 주문+결제 (잔액 부족 시 비활성화)
│        └──────────────────┘          │
│                                      │
│  📍 현재 위치: 가맹점 반경 내 ✅      │  ← GPS 검증 상태
│  ℹ️ 결제 완료 시 매장에 주문이 전달됩니다│
```

**주문+결제 워크플로우**:
1. 가맹점 상세 → "주문하기" 버튼 → OrderScreen 진입
2. 이용 방식 선택 (매장 식사 / 포장)
3. 메뉴 + 옵션 선택, 수량 조절
4. Split Payment 자동 계산 (회사/개인 분담 실시간 표시)
5. GPS 위치 검증 (가맹점 반경 내 확인)
6. "주문·결제하기" → `mealOrderCreate` mutation 호출
7. 결제 성공 → OrderStatusScreen 전환 ("매장 확인 중...")
8. 결제 실패 → 에러 표시 (잔액 부족, 시간대 외, GPS 범위 외 등)

**RFID 배지 결제** (Closed Loop):
- RFID 결제는 POS에서 직접 처리 (앱 관여 없음)
- 결제 완료 시 `mealTransactionResult` Subscription으로 앱에 알림
- 앱은 결과 푸시만 수신 + 잔액 자동 갱신

1. 금액 선택/입력
2. 결제 수단 선택 (NAPAS QR / VISA·MC / MoMo / ZaloPay / 은행이체)
3. 결제 수단별 분기:
   - **NAPAS QR**: 결제 QR 생성 → 사용자 은행앱으로 스캔 → Webhook 수신
   - **VISA/MC**: PG 결제 페이지 (WebView 또는 SDK) → 결제 → Webhook 수신
   - **MoMo/ZaloPay**: 딥링크 호출 → 결제 완료 콜백 수신
   - **은행 이체**: 가상계좌 표시 → 입금 확인 (수동/자동)
4. 서버 `mealWalletTopUp` mutation 호출
5. `personalTopUpVnd` bucket 증가 반영
6. TopUpResultScreen으로 전환

> **주문 및 식권 이용은 반드시 결제(충전) 완료 후에만 가능하다.** 잔액 부족 시 충전을 유도한다.

> **부분 성공 허용 원칙**: 각 참여자의 `mealOrderCreate`는 **독립적**이다. 한 명의 실패가 다른 사람의 주문에 영향을 주지 않는다. 전체 롤백하지 않는다.

## 6. 결제 엔진

### 6.1 결제 방식 분류

| 방식 | 환경 | 흐름 | 처리 시간 | 네트워크 |
|------|------|------|----------|---------|
| **앱 내 주문+결제** (기본) | 도심 제휴 식당 | 앱에서 메뉴 선택 → 결제 → 주문 전달 | ≤ 3초 | 온라인 필수 |
| **RFID 배지** | 구내식당, 공장 | 배지 태그 → POS 자동 승인 | ≤ 0.8초 | 온라인/오프라인 |

> **설계 변경 (v2.0)**: 기존 "앱에서 QR 생성 → POS가 스캔" 방식을 폐기하고, **앱 내 직접 주문+결제** 방식으로 변경.
> 이유: 가맹점이 이미 플랫폼 서버와 연동되어 있고, 지갑 잔액이 서버에 존재하므로 QR 중간 단계가 불필요.
> **주문은 반드시 결제 완료 후에만 POS(가맹점주)에게 전달된다.**

#### 6.2.1.1 예정 방문/픽업 시간

주문 시 임직원은 **예정 방문 시간**(매장 식사) 또는 **픽업 예정 시간**(포장)을 반드시 선택해야 한다.

**앱 UI — 시간 선택:**
```
┌──────────────────────────────────────┐

│                                      │
│  [11:00] [11:30] [12:00] [12:30]    │  ← 30분 단위 슬롯
│  [13:00] [13:30] [14:00] [직접입력]  │
│                                      │
│  🪑 12:00 빈 테이블 8/20석           │  ← POS 연동 매장만 실시간 표시
│  ⏱️ 평균 식사 시간: 약 35분           │  ← POS 테이블 점유 데이터 기반
│  ℹ️ 선택한 시간에 맞춰 조리를 시작합니다│

```

**슬롯 관리:**

| 항목 | 설명 | 설정 주체 | POS 연동 필요 |
|------|------|----------|-------------|
| 슬롯 간격 | 30분 (기본) / 15분 / 1시간 — 매장별 설정 | 가맹점 (POS/BrandAdmin) | ❌ |
| 운영 시간 | 매장 영업시간 내 슬롯만 표시 | `Branch.businessHoursJson` | ❌ |
| 마감 시간 | 슬롯 시작 N분 전 주문 마감 (기본 30분 전) | 가맹점 | ❌ |
| **실시간 빈 테이블** | 슬롯별 빈 테이블 수 / 전체 테이블 수 | POS 테이블 상태 (`VACANT` 카운트) | ✅ **POS 연동 매장만** |
| **평균 식사 시간** | 해당 매장의 평균 테이블 점유 시간 (분) | POS 테이블 생성~종료 이력 집계 | ✅ **POS 연동 매장만** |
| **피크타임 경고** | 잔여석 적을 때 경고 표시 | POS 테이블 점유율 | ✅ **POS 연동 매장만** |

**POS 연동 여부에 따른 앱 표시:**

| 매장 상태 | 시간 슬롯 | 좌석 정보 |
|----------|----------|----------|
| **POS 연동됨** | 슬롯 표시 + **실시간 빈 테이블** (예: "🪑 8/20석") | POS `TABLE:GET_ALL`에서 `VACANT` 상태 카운트 |
| **POS 미연동** | 슬롯 표시만 (좌석 정보 없음) | 표시 안 함 |

**서버 처리:**
- `MealOrderCreateInput`에 `scheduledAt: DateTime!` 필드 추가
- 매장이 슬롯별 수용량을 초과하면 해당 슬롯 비활성화
- POS 연동 매장: `branchTableAvailability(branchId, scheduledAt)` query로 빈 테이블 수 + 평균 점유 시간 반환
- POS 미연동 매장: 좌석/점유 정보 미제공 (슬롯만 운영)

**평균 테이블 점유 시간 계산 (POS 연동 매장):**
```
데이터 소스: POS 테이블 이벤트 (TABLE:SELECT → 점유 시작, TABLE:CLOSE → 점유 종료)

계산:
  avgOccupancyMin = AVG(closeAt - selectAt)
                    WHERE branchId = ? AND closeAt IS NOT NULL
                    AND createdAt >= NOW() - INTERVAL '30 days'  -- 최근 30일 데이터

반환: branchTableAvailability.avgOccupancyMin (정수, 분 단위)

앱 표시: "⏱️ 평균 식사 시간: 약 {avgOccupancyMin}분"
```

**캐시**: 평균 점유 시간은 실시간 변동 아님 → Redis TTL 1시간 캐시
- POS: 시간대별 주문 목록 정렬, 조리 시작 타이밍 자동 계산


#### 6.2.1.2 테이블 체크인 — 서빙 연동 (매장 식사) — `⚙️ 백엔드 선행 구현 (POS 프론트 미시작)`

베트남 식당은 **직원이 테이블로 직접 서빙**하는 문화이므로, 매장 직원이 **어느 테이블에 가져다줘야 하는지** 알아야 한다. 매장 직원에게 추가 업무를 주지 않고, **임직원이 직접 테이블 체크인**하는 방식으로 해결한다.

**흐름:**
```
[임직원]                  [앱]                [CentralApi]          [POS]
    │                       │                      │                  │
    │── 매장 도착, 착석 ────│                      │                  │
    │                       │                      │                  │
    │── 테이블 QR 스캔 ────>│                      │                  │
    │   (테이블 5번)        │── checkin ──────────>│                  │
    │                       │   (orderId, tableNo) │── 주문 업데이트 ─>│
    │                       │                      │   #A-042 → T-5   │
    │                       │<── 완료 ─────────────│                  │
    │                       │                      │                  │
    │                       │   앱: "테이블 5번     │   POS 주문 카드:  │
    │                       │   체크인 완료 ✅"     │   쌀국수 → T-5   │
    │                       │                      │                  │
    │                       │                      │   직원이 T-5로    │
    │                       │                      │   서빙 ──────────>│
```

**테이블 QR 스티커:**
- 각 테이블에 고정 QR 부착: `vmeal://table/{branchId}/{tableNo}`
- 가맹점 등록 시 SuperAdmin Portal에서 **테이블 QR 일괄 생성 + 인쇄용 PDF 다운로드** 제공
- QR에는 테이블 번호만 인코딩 (보안 코드 불필요 — 매장 내 물리 접근 = 현장 증명)

**임직원 앱 — 체크인:**

**POS 주문 카드 (테이블 정보 포함):**
```

│ 김민수 (ABC기업)  12:00      │

```

**서빙 확인 방식 — 매장별 선택 (2가지):**

가맹점은 BrandAdmin/POS에서 자사 매장에 맞는 방식을 선택한다.

| 방식 | 매장 설정 | 흐름 | 적합 매장 |
|------|----------|------|----------|
| **A. 테이블 QR 체크인** (기본) | `tableCheckInMode: QR_CHECKIN` | 임직원이 앱으로 테이블 QR 스캔 → 자동 매칭 → 직원이 테이블로 서빙 | 테이블 QR 부착 가능한 매장 |
| **B. POS 매대 확인** | `tableCheckInMode: POS_CONFIRM` | 임직원이 식사 후 퇴장 전 POS 매대 방문 → 앱 주문번호 제시 → 직원이 POS에서 테이블 매칭 + 이용 완료 처리 | QR 부착 원치 않는 매장 |

#### 방식 A: 테이블 QR 체크인 (위 설명과 동일)

- 체크인은 **서빙 보조용** — 주문 상태 전이와 무관
- 체크인하지 않아도 주문 진행에 문제 없음 (주문번호 호출로 서빙)
- 체크인 시: POS에 테이블 번호 표시 → 직원이 해당 테이블로 서빙
- **`COMPLETED` 전환은 체크인이 아니라 POS에서 [이용 완료] 클릭 시에만 발생**
- 포장(`TAKEOUT`)은 체크인 불필요

#### 방식 B: POS 매대 확인 (테이블 QR 미사용 매장) — `⚙️ 백엔드 선행 구현 (POS 프론트 미시작)`

테이블 QR을 두지 않는 매장에서 사용. 임직원이 식사를 마치고 퇴장하기 전에 POS 매대에서 확인.

**흐름:**
```
[임직원]              [POS 매대 직원]              [POS]
    │                       │                       │
    │── 매장 도착, 착석 ────│                       │
    │                       │                       │
    │   (음식 서빙 — 주문번호 기준 또는 순서대로)     │
    │                       │                       │
    │── 식사 완료 ──────────│                       │
    │                       │                       │
    │── POS 매대 방문 ─────>│                       │
    │   앱 주문번호 제시     │                       │
    │   (#A-042)            │                       │
    │                       │── POS에서 주문 검색 ──>│
    │                       │   #A-042 선택          │
    │                       │   [테이블 선택] → T-5   │
    │                       │   [이용 완료] 클릭      │
    │                       │                       │
    │<── "감사합니다" ──────│<── 완료 처리 ─────────│
    │                       │                       │
```

**POS 화면 — 방식 B:**
```
┌──────────────────────────────────────┐
│ 미확인 주문 (이용 완료 대기)          │
├──────────────────────────────────────┤
│                                      │
│  #A-042  김민수 (ABC기업)  🍽️ 매장   │
│  쌀국수 x1, 아이스커피 x1  ₫105,000 │
│  예정: 12:00  수락: 12:02            │
│  ┌──────────┐ ┌────────────────────┐│
│  │ 테이블: [▼ T-5] │ [✅ 이용 완료]  ││  ← 직원이 테이블 선택 + 완료 클릭
│  └──────────┘ └────────────────────┘│
│                                      │
│  #A-043  박영희 (DEF기업)  📦 포장   │
│  비빔밥 x2             ₫130,000     │
│  예정: 12:30  수락: 12:05            │
│  ┌────────────────────┐             │
│  │ [✅ 수령 완료]       │             │  ← 포장은 테이블 선택 없이 바로 완료
│  └────────────────────┘             │
│                                      │
└──────────────────────────────────────┘
```

**방식 B의 장점:**
- 테이블 QR 스티커 불필요 — 매장 인테리어 영향 없음
- 매장 직원이 기존 POS 워크플로우(테이블 관리) 그대로 사용
- 임직원 퇴장 전 POS 매대 방문은 "계산대에서 확인" 동선과 자연스러움

**방식 B의 서빙 방법:**
- 조리 완료 시 POS에 주문번호 표시 → 직원이 "42번 나왔습니다" 호출 또는 순서대로 서빙
- 테이블 매칭은 **식사 후 확인 시점**에 처리 (서빙 전이 아님)
- **테이블 입력 + [이용 완료] 클릭 = 동일 동작으로 `COMPLETED` 전환** (2단계 아님, 1클릭)

**매장 설정 (BrandAdmin/POS):**
```prisma
// Branch 또는 MealMerchantEnrollment에 추가
tableCheckInMode String @default("QR_CHECKIN") @db.VarChar(20) // QR_CHECKIN | POS_CONFIRM | NONE
```

**DB:**
```prisma

```

**GraphQL:**
```graphql

  mealOrderCheckin(orderId: $orderId, tableNo: $tableNo) {
    success { data { id tableNo checkedInAt } }
    error { code message }
  }
}
```

### 6.2.2 주문 수락 워크플로우 — `⚙️ 백엔드 선행 구현 (POS 프론트 미시작)`

> **결제 완료 ≠ 주문 확정.** 매장이 주문을 수락해야 조리가 시작된다.

```
[임직원 앱]          [CentralApi]          [POS/가맹점]
    │                     │                      │
    │── 주문+결제 ───────>│                      │
    │<── PAID_PENDING_ACCEPT │                      │
    │   "매장 확인 중..."  │── 주문 푸시 ────────>│
    │                     │   (알림음 + 팝업)     │
    │                     │                      │
    │                     │   매장 직원 확인      │
    │                     │                      │
    │  [취소 가능]         │<── [수락] ───────────│
    │<── ACCEPTED ────────│                      │
    │   "주문 수락됨 🎉"   │                      │
    │                     │                      │
    │                     │<── [조리 시작] ───────│
    │<── PREPARING ───────│                      │
    │   "조리 중... 🍳"    │                      │
    │                     │                      │
    │                     │<── [준비 완료] ───────│
    │<── READY ───────────│                      │
    │   "준비 완료!        │                      │
    │    주문번호 #A-042   │                      │
    │    수령해주세요"      │                      │
    │                     │                      │
    │── [수령 확인] ──────>│── COMPLETED ────────>│
    │<── 완료 ────────────│                      │
```

### 6.2.2 주문 상태 머신

```
PAID_PENDING_ACCEPT → ACCEPTED → PREPARING → READY → COMPLETED
      │                                                  │
      ├── CANCELLED_BY_USER (임직원 직접 취소)             │
      ├── REJECTED (매장 거절)                             │
      └── EXPIRED (제한시간 초과)                           │
                                                          │
      CANCELLED/REJECTED/EXPIRED → REFUNDED (자동 전액 환불)
```

**상태값 목록 (8개):**

| 상태 | 설명 | 다음 가능 상태 | 앱 표시 |
|------|------|---------------|--------|
| `PAID_PENDING_ACCEPT` | 결제 완료, 매장 수락 대기 | → `ACCEPTED`, `CANCELLED_BY_USER`, `REJECTED`, `EXPIRED` | "매장 확인 중..." + 취소 버튼 |
| `ACCEPTED` | 매장 수락 완료 | → `PREPARING` | "주문 수락됨 🎉" |
| `PREPARING` | 조리 중 | → `READY` | "조리 중... 🍳" |
| `READY` | 준비 완료 | → `COMPLETED` | "준비 완료! 주문번호 #A-042" |
| `COMPLETED` | 이용 완료 (매장 식사 완료 or 포장 수령) | 종결 | "식사를 즐겨주세요 😋" |
| `CANCELLED_BY_USER` | 임직원이 직접 취소 | → `REFUNDED` | "주문이 취소되었습니다" |
| `REJECTED` | 매장이 거절 | → `REFUNDED` | "매장 사정으로 주문이 거절되었습니다" |
| `EXPIRED` | 매장 미응답 (제한시간 초과) | → `REFUNDED` | "매장이 응답하지 않아 자동 취소되었습니다" |

**상태 전이 규칙 — 체크인/서빙과의 관계:**
- 테이블 체크인(`mealOrderCheckin`)은 **상태 전이를 일으키지 않음** — 서빙 보조 정보일 뿐
- `COMPLETED` 전환은 오직 **POS에서 [이용 완료] 또는 [수령 완료] 클릭 시에만** 발생
- `QR_CHECKIN` 방식: 체크인 → (서빙) → POS [이용 완료] → `COMPLETED`
- `POS_CONFIRM` 방식: (서빙) → 임직원 퇴장 전 POS 매대 [테이블 선택 + 이용 완료] → `COMPLETED` (1클릭)
- `NONE` 방식 (구내식당): 조리+서빙 완료 시 POS [이용 완료] → `COMPLETED`

### 6.2.3 수락 제한 시간 및 임직원 취소

**매장 수락 제한 시간:**

| 주문 유형 | 제한 시간 | 미응답 처리 |
|----------|----------|------------|
| **현장 주문** (매장 내에서 주문) | **10분** | 자동 `EXPIRED` → 환불 |
| **사전 주문** (방문 전 미리 주문) | **1시간** | 자동 `EXPIRED` → 환불 |

**임직원 직접 취소 규칙:**

취소 정책은 **가맹점(제휴식당)이 직접 설정**한다. 임직원은 주문 전 취소 정책을 확인할 수 있다.

#### 가맹점 취소 정책 설정 (BrandAdmin/POS)

| 설정 | 필드 | 옵션 | 기본값 |
|------|------|------|--------|
| 취소 허용 모드 | `cancellationMode` | `FREE_UNTIL_ACCEPTED` / `FREE_UNTIL_DEADLINE` / `NO_CANCEL` | `FREE_UNTIL_ACCEPTED` |
| 취소 마감 시간 | `cancellationDeadlineMin` | 예정 방문 시간 N분 전까지 취소 가능 | 30 (분) |

**취소 모드 상세:**

| 모드 | 설명 | 취소 가능 시점 |
|------|------|--------------|
| `FREE_UNTIL_ACCEPTED` | 매장 수락 전까지 자유 취소 **(기본)** | 상태 = `PAID_PENDING_ACCEPT`일 때만 |
| `FREE_UNTIL_DEADLINE` | 예정 방문 시간 N분 전까지 취소 가능 | 매장 수락 후에도 마감 시간 전이면 취소 가능 |
| `NO_CANCEL` | 결제 후 취소 불가 | 결제 완료 즉시 취소 불가 (환불 없음) |

**DB (MealMerchantEnrollment 확장):**
```prisma
cancellationMode         String @default("FREE_UNTIL_ACCEPTED") @db.VarChar(30)
cancellationDeadlineMin  Int    @default(30) // FREE_UNTIL_DEADLINE 모드에서만 사용
```

#### 주문 전 취소 정책 안내 (앱 UI)

임직원이 주문·결제하기 버튼을 누르기 전에 해당 가맹점의 취소 정책을 표시한다.

```
┌──────────────────────────────────────┐
│  ─── 결제 요약 ─────────────────── │
│  총 금액                   ₫105,000 │
│  ├ 회사 지원금 차감        ₫100,000 │
│  └ 개인 충전 차감           ₫5,000  │
│                                      │
│  ─── 취소 정책 ─────────────────── │
│  ℹ️ 매장 수락 전까지 취소 가능       │  ← FREE_UNTIL_ACCEPTED
│  또는                                │
│  ⚠️ 예정 방문 30분 전까지 취소 가능  │  ← FREE_UNTIL_DEADLINE
│  또는                                │
│  🚫 결제 후 취소 불가                │  ← NO_CANCEL (빨간색 경고)
│                                      │
│        ┌──────────────────┐          │
│        │ ₫105,000 주문·결제하기│       │
│        └──────────────────┘          │
└──────────────────────────────────────┘
```

#### 임직원 취소 판정 로직 (서버)

```
mealOrderCancel(orderId) 호출 시:

1. 주문 조회 → 가맹점의 cancellationMode 확인
2. 모드별 판정:

   FREE_UNTIL_ACCEPTED:
     상태 = PAID_PENDING_ACCEPT → ✅ 취소 + 전액 환불
     상태 = ACCEPTED 이후 → ❌ 거절 (ORDER_CANCEL_NOT_ALLOWED)

   FREE_UNTIL_DEADLINE:
     현재시각 < scheduledAt - cancellationDeadlineMin → ✅ 취소 + 전액 환불
     현재시각 ≥ 마감 시간 → ❌ 거절 (ORDER_CANCEL_DEADLINE_PASSED)

   NO_CANCEL:
     항상 → ❌ 거절 (ORDER_CANCEL_NOT_ALLOWED)
```

#### 취소 가능 상태 요약

| 조건 | FREE_UNTIL_ACCEPTED | FREE_UNTIL_DEADLINE | NO_CANCEL |
|------|---------------------|---------------------|-----------|
| `PAID_PENDING_ACCEPT` | ✅ 취소 가능 | ✅ (마감 전) | ❌ 불가 |
| `ACCEPTED` (수락됨) | ❌ 불가 | ✅ (마감 전) / ❌ (마감 후) | ❌ 불가 |
| `PREPARING` 이후 | ❌ 불가 | ❌ 불가 | ❌ 불가 |

**취소 시 환불 처리:**
```
1. 주문 상태 → CANCELLED_BY_USER / REJECTED / EXPIRED
2. MealTransaction.status → REVERSED
3. Wallet 잔액 복원:
   - companyAllowanceVnd += companyShareVnd (원래 차감분)
   - personalTopUpVnd += employeeShareVnd (원래 차감분)
4. 앱 Push 알림: "주문이 취소되었습니다. ₫{amount} 환불 완료"
5. AuditLog 기록
```

**앱 UI — 취소 버튼:**

### 6.2.4 부정결제 방지 (Fraud Prevention)

| 검증 항목 | 방식 | 설명 |
|----------|------|------|
| **GPS 위치 검증** | 결제 시 임직원 GPS 좌표 vs 가맹점 좌표 비교 | 반경 500m 이내만 결제 허용 (설정 가능) |
| **시간대 검증** | 정책 엔진의 allowedTimeStart/End 적용 | 식사 시간대 외 결제 차단 |
| **기기 바인딩** | deviceId 등록 (1인 1기기 원칙) | 동일 계정 다중 기기 로그인 시 기존 기기 세션 종료 |
| **이상 거래 탐지** | 동일 시간대 다중 결제, 비정상 패턴 감지 | 5분 내 2건 이상 결제 시 추가 인증 요구 |
| **금액 상한** | 1회 한도 + 일일 한도 (정책 엔진) | maxPerTransactionVnd, dailyLimitVnd |

> **추가 기획 필요**: GPS 스푸핑 방지, 실내 위치 정확도 개선 (Wi-Fi 기반), 기업별 허용 반경 커스터마이징

### 6.2.5 가맹점 노출 규칙

```
플랫폼 전체 제휴 가맹점 (MealMerchantEnrollment.isActive = true)
  └── 필터: 소속 기업이 등록/허용한 식당만 노출
       └── 필터: 임직원 정책의 allowedMerchantCategoryIds 적용
            └── 필터: GPS 기반 거리순 정렬
```

**노출 우선순위:**
1. 소속 기업(CorporatePortal)에서 **명시적으로 등록/허용한 가맹점만** 노출
2. 기업이 특별히 설정하지 않은 경우 → 플랫폼 전체 활성 가맹점 중 기업 정책에 부합하는 것만
3. 비활성(`isActive = false`) 가맹점은 어떤 경우에도 노출 불가

### 6.3 Split Payment (하이브리드 결제) 로직

**2-Bucket 차감 순서**:
1. 회사 지원금(`companyAllowanceVnd`) 우선 차감
2. 부족분은 개인 충전(`personalTopUpVnd`)에서 차감
3. 양쪽 모두 부족 → `INSUFFICIENT_BALANCE` 거절

**예시**:
| 시나리오 | 요청 금액 | 회사 잔액 | 개인 잔액 | 회사 차감 | 개인 차감 | 결과 |
|---------|----------|----------|----------|----------|----------|------|
| 회사 잔액 충분 | ₫100K | ₫200K | ₫50K | ₫100K | ₫0 | 승인 |
| Split 필요 | ₫150K | ₫100K | ₫100K | ₫100K | ₫50K | 승인 |
| 잔액 부족 | ₫150K | ₫50K | ₫50K | - | - | 거절 |
| Split 비허용 | ₫150K | ₫100K | ₫100K | - | - | 거절 (정책) |

### 6.4 멱등성 (Idempotency)

- 모든 결제 요청에 `idempotencyKey` 필수 포함
- 형식: `{walletId}:{timestamp}:{nonce}`
- 서버는 동일 키 재요청 시 기존 결과 반환 (중복 차감 방지)
- DB: `MealTransaction.idempotencyKey` UNIQUE 제약

### 6.5 결제 취소

**취소 권한 분리:**
- **주문 취소** (`mealOrderCancel`): 임직원이 앱에서 직접 가능 — `PAID_PENDING_ACCEPT` 상태에서만 (매장 수락 전). 즉시 전액 환불.
- **거래 역전** (`mealTransactionReverse`): 관리자(SuperAdmin/BrandAdmin) 전용. 이미 승인된 거래(`APPROVED`)의 사후 취소. 정산에 영향.

주문 취소 시:
- 주문 상태 → `CANCELLED_BY_USER` → 자동 `REFUNDED`
- 지갑 잔액 복원 (funding entry 역전)
- 임직원 앱에 푸시 알림으로 환불 완료 안내

거래 역전 시:
- `MealTransaction.status` → `REVERSED` → 지갑 잔액 복원
- 임직원 앱은 푸시 알림으로 취소 사실 수신

## 7. 정책 엔진 연동

### 7.1 정책 평가 시점

결제 승인 시 서버(CentralApi)가 다음 순서로 정책 검증:

```
1. 임직원 상태 검증 (MealEmployee.status === 'ACTIVE')
2. 지갑 상태 검증 (MealWallet.status === 'ACTIVE')
3. 가맹점 상태 검증 (MealMerchantEnrollment.isActive === true)
4. 정책 매칭 (corporateId + departmentId + roleCode → 해당 정책 필터)
5. 시간 검증 (현재 시각이 allowedTimeStart ~ allowedTimeEnd 범위)
6. 요일 검증 (현재 요일이 allowedDayOfWeek 배열에 포함)
7. 가맹점 카테고리 검증 (merchantCategoryRestrictions 매칭)
8. 1회 한도 검증 (requestedAmountVnd ≤ maxPerTransactionVnd)
9. 일일 한도 검증 (오늘 누적 + 요청 ≤ dailyLimitVnd)
10. Split Payment 허용 검증 (allowSplitPayment)
```

### 7.2 앱 사전 검증 (UX 개선)

서버 검증 전에 앱에서 사전 안내하여 거절 경험 최소화:

| 검증 항목 | 앱 표시 | 타이밍 |
|----------|--------|-------|
| 사용 불가 시간 | 주문 버튼에 "11:00부터 사용 가능" 표시 | WalletHomeScreen 로드 시 |
| 사용 불가 요일 | 주문 버튼 비활성화 + 안내 문구 | WalletHomeScreen 로드 시 |
| 일일 한도 소진 | "오늘의 한도를 모두 사용했습니다" | 결제 시도 전 |
| 가맹점 카테고리 제한 | 정책의 카테고리 제한에 해당하는 식당은 목록에서 제외 | 식당 목록 로드 시 |

### 7.3 위치 검증 (부정결제 방지)

> 이 앱은 **제휴 가맹점만 노출**하므로 구역별 허용/제한 구분은 불필요.
> GPS 검증은 "매장 근처에 있는지" 확인하는 **부정결제 방지** 목적으로만 사용한다 (§6.2.4 참조).

- 주문 시 임직원 GPS 좌표를 서버로 전송
- 서버에서 가맹점 좌표와 비교 → 허용 반경(기본 500m, 매장별 설정 가능) 초과 시 주문 거절
- GPS 오차 보완: §F.3 체크인 QR fallback (실내 식당 대응)

```
│                                     │
```

### 8.2 Funding Entry 원장

모든 잔액 변동은 `MealWalletFundingEntry`에 이력 기록:

| sourceType | 설명 | 발생 시점 |
|-----------|------|----------|
| `COMPANY_ALLOWANCE` | 회사 지원금 적립 | 매월 1일 자동 또는 관리자 수동 |
| `PERSONAL_TOP_UP` | 개인 충전 | 임직원이 e-Wallet으로 충전 시 |

| status | 설명 |
|--------|------|
| `PENDING` | 입금 대기 (은행 이체 확인 전) |
| `POSTED` | 적립 완료 (잔액 반영) |
| `REVERSED` | 취소/환불 |

### 8.3 잔액 갱신 이벤트

앱에서 잔액이 갱신되는 시점:
1. **앱 진입 시**: `mealWallet` 쿼리 (cache-and-network)
2. **결제 완료 후**: 결제 응답의 잔액 반영 → Apollo 캐시 업데이트
3. **충전 완료 후**: TopUp 응답의 잔액 반영
4. **푸시 알림 수신 시**: `WALLET_FUNDED` 이벤트 → 쿼리 refetch
5. **Pull-to-Refresh**: 수동 갱신
6. **포그라운드 복귀 시**: 자동 refetch

### 10.4.2 mealOrderCreate 서버 처리 흐름

```
1. 멱등성 검증 (idempotencyKey)
2. 부정결제 방지 검증:
   a. GPS 위치 검증: userLat/Lng vs Branch.latitude/longitude → 허용 반경 내?
   b. 시간대 검증: 정책 엔진 allowedTimeStart/End
   c. 기기 바인딩: deviceId 검증 (1인 1기기)
   d. 이상 거래: 5분 내 2건 이상 → 추가 인증 요구
3. 정책 검증 (evaluateForEmployee)
4. 잔액 검증 + Split Payment 분배
5. Wallet 차감 (DB 트랜잭션)
6. MealTransaction 생성 (status: APPROVED)
7. MealOrder 생성 (status: PAID_PENDING_ACCEPT)
8. POS에 주문 푸시 (GraphQL Subscription: mealOrderReceived)
9. 타이머 시작 (현장 10분 / 사전 1시간 → 미수락 시 자동 EXPIRED + 환불)
10. 응답 반환
```

| 슬라이스 | 저장 항목 | 용도 |

### 12.3 오프라인 결제 — 전면 불가

> **모든 결제/주문은 온라인 필수. 오프라인 결제는 어떤 방식으로도 허용하지 않는다.**

**이유:**
- 잔액의 원본(source of truth)은 **서버 DB** — 앱/POS 캐시 잔액은 정확성을 보장할 수 없음
- 오프라인에서 잔액 차감 시 **실제 잔액 0원인데 결제 승인**되는 위험
- RFID 오프라인 차감 후 앱 온라인 결제 시 **이중 차감/잔액 불일치** 발생
- 돈과 관련된 모든 트랜잭션은 **서버 검증 후에만 승인** — 이 원칙은 타협 불가

**방식별 정책:**

| 방식 | 오프라인 결제 | 이유 |
|------|-------------|------|
| **앱 내 주문+결제** | ❌ **불가** | `mealOrderCreate`는 서버 mutation — 온라인 필수 |
| **RFID 배지** | ❌ **불가** | POS도 서버 `mealTransactionAuthorize` 호출 필수 |
| **사전주문** | ❌ **불가** | 서버에서 Hold + 결제 처리 |

**네트워크 불안정 환경 대응 (오프라인 결제 대신):**
- 구내식당 POS: **유선 인터넷 필수** (Wi-Fi 불안정 시 LAN 케이블)
- 공장: 전용 네트워크 or 모바일 핫스팟 비상용
- 네트워크 장애 시: 주문/결제 **진입 차단** + "네트워크 연결 필요" 안내

### 12.4 네트워크 상태 감지

`@react-native-community/netinfo`로 실시간 감지:

| 상태 | 앱 동작 |
|------|--------|
| 온라인 | 정상 운영 |
| 오프라인 | 상단 배너 "오프라인 상태" + 앱 결제 비활성화 |
| 온라인 복귀 | 캐시 무효화 + 전체 refetch + 배너 해제 |

- 무한 스크롤: 페이지 크기 20건, 다음 페이지 prefetch

### 14.0 OS 권한 요청 (Permission)

#### 백엔드 연동

권한 자체는 클라이언트 전용이지만, 서버에 **권한 상태를 기록**하여 기능 분기에 활용:

```graphql
mutation mealEmployeeUpdateDeviceInfo($input: DeviceInfoInput!) {
  mealEmployeeUpdateDeviceInfo(input: $input) {
    success { data { id } }
    error { code message }
  }
}

input DeviceInfoInput {
  deviceId: String!
  platform: String!          # IOS | ANDROID
  fcmToken: String
  locationPermission: String! # GRANTED | DENIED | NOT_DETERMINED
  cameraPermission: String!
  notificationPermission: String!
  biometricAvailable: Boolean!
  biometricType: String       # FACE_ID | TOUCH_ID | FINGERPRINT | null
}
```

- 앱 시작 시 + 권한 변경 시 `mealEmployeeUpdateDeviceInfo` 호출
- 서버: `locationPermission = DENIED`인 사용자에게 GPS 검증 생략 가능 여부 정책 판단
- 서버: `notificationPermission = DENIED`인 사용자에게 이메일 알림 대체 발송

### 14.1 인증 보안

| 항목 | 구현 |
|------|------|
| Access Token | 메모리 전용, AsyncStorage 저장 금지 |
| Refresh Token | HttpOnly 쿠키, Secure 플래그 |
| 생체 인증 | Secure Enclave (iOS) / StrongBox (Android) |
| PIN 코드 | 생체 인증 불가 시 대체 수단 |
| 세션 만료 | 비활성 30분 → 자동 잠금 (생체 재인증) |

### 14.2 결제 보안

| 항목 | 구현 |
|------|------|
| 체크인 QR 토큰 | 서버 서명, 10분 유효, 1회용 — 체크인 QR fallback(F.3) 전용. 결제용 QR 아님 |
| 스크린샷 방지 | 결제 화면에서 `FLAG_SECURE` / `isSecureTextEntry` |

| RFID 도용 감지 | 사원증 결제 시 즉시 푸시 → "방금 결제하셨나요?" |
| 이상 결제 감지 | 단시간 중복 / 지역 이탈 결제 → 관리자 알림 |

| 항목 | 구현 |
|------|------|
| 전송 암호화 | TLS 1.3 필수 |
| 로컬 저장 | 민감 데이터는 Keychain (iOS) / EncryptedSharedPreferences (Android) |
| 로그 | 프로덕션에서 개인정보/토큰 로깅 금지 |

### 14.4 개인정보 보호

- 전화번호: E.164 형식 저장, UI에서 부분 마스킹
- RFID 번호: UI에서 마스킹 (****XXXX)
- **위치 정보 처리 정책:**
  - 결제/주문 시 임직원 GPS 좌표를 서버에 전송하여 부정결제 검증에 사용한다.
  - 좌표는 `MealOrder.userLatitude/userLongitude`에 저장한다.
  - **보관 기간**: 거래일로부터 60일. 이후 좌표 필드 NULL 처리 (마스킹).
  - **접근 권한**: SuperAdmin 감사 목적으로만 조회 가능. 임직원/기업관리자에게 노출 불가.
  - **앱 동의**: 최초 결제 시 위치정보 수집 동의 팝업 필수 (PDPD 준수).
  - **정밀도**: 소수점 4자리까지만 저장 (약 11m 정밀도) — 정확한 위치 추적 방지.
- 생체 데이터: 디바이스 Secure Enclave에서만 처리, 서버 전송 없음

## 19. 오늘의 메뉴 및 사전주문

### 19.1 기능 개요

구내식당(Closed Loop 가맹점)이 매일 조식/중식/석식 메뉴를 일괄 등록하면, **해당 가맹점을 구독한 임직원에 한해** 푸시 알림으로 안내하고, 임직원이 앱에서 끼니별로 사전주문하여 구내식당이 미리 준비할 수 있는 기능이다.

> 전체 비즈니스 워크플로우는 상위 문서 `프로젝트 개요.md § 7. 오늘의 메뉴 및 사전주문 워크플로우`를 참조한다.

**핵심 원칙**:
- 푸시 알림은 **가맹점을 구독한 임직원에게만** 전송한다 (Opt-in 방식)
- 가맹점은 **조식/중식/석식을 한번에** 등록하며, DailyMenu 1건에 3끼가 모두 포함된다
- 임직원은 **3끼 메뉴를 한 화면에서 탭으로 전환**하여 확인하고, **각 끼니별로 독립 사전주문** 가능

### 19.2 가맹점 구독 모델

#### 데이터 모델 (신규)

```
MealMerchantSubscription
├── id: UUID (PK)
├── employeeId: UUID (FK → MealEmployee)
├── branchId: UUID (FK → Branch)        ← 가맹점 지점 단위 구독
├── isActive: Boolean                   ← 구독 ON/OFF
├── notifyBreakfast: Boolean (default true)
├── notifyLunch: Boolean (default true)
├── notifyDinner: Boolean (default true)
├── createdAt: Timestamptz
├── updatedAt: Timestamptz
└── Unique: (employeeId, branchId)      ← 1인 1가맹점 1구독
```

#### 구독 워크플로우

```
임직원이 가맹점 상세(MerchantDetailScreen) 또는
오늘의 메뉴 화면(DailyMenuScreen)에서 구독 버튼 탭
    │
    ▼
mealMerchantSubscribe mutation 호출
    │
    ▼
MealMerchantSubscription 레코드 생성 (isActive: true)
    │
    ▼
이후 해당 가맹점이 DailyMenu 발행 시
→ 구독자(isActive: true) 목록 조회
→ 끼니별 알림 설정(notifyBreakfast/Lunch/Dinner) 필터
→ **큐 기반 배칭 알림** (아래 §19.2.1 참조)
```

#### 구독 해제

- 임직원이 언제든 구독 해제 가능 (`mealMerchantUnsubscribe`)
- 해제 시 `isActive: false`로 변경 (soft delete)
- 재구독 시 기존 레코드 `isActive: true`로 복원

#### 19.2.1 푸시 알림 배칭 (Batched Notification)

> **문제**: 구독 가맹점이 10개이고 10개가 동시에 중식 메뉴를 발행하면 → 10개 푸시가 연달아 도착 → 알림 폭탄

**해결: 끼니별 배칭 큐**

```
[가맹점 A 중식 메뉴 발행] ──┐
[가맹점 B 중식 메뉴 발행] ──┤  Redis Queue
[가맹점 C 중식 메뉴 발행] ──┤  (5분 집계 윈도우)
[가맹점 D 중식 메뉴 발행] ──┘
                              │
                              ▼ (5분 후 배칭)
                    ┌────────────────────┐
                    │  FCM 푸시 1건       │
                    │  "오늘의 중식 메뉴  │
                    │   4개 매장 업데이트" │
                    └────────────────────┘
```

**배칭 규칙:**

| 항목 | 설정 | 설명 |
|------|------|------|
| 집계 윈도우 | **5분** | 동일 끼니 메뉴 발행을 5분간 모아서 1건으로 전송 |
| 최대 대기 | 10분 | 5분 내 추가 발행이 없으면 즉시 전송 |
| 끼니별 분리 | 조식/중식/석식 | 각 끼니는 독립 큐로 관리 |
| 배칭 단위 | 임직원별 | 임직원 A의 구독 가맹점끼리 배칭 |

**푸시 내용 (배칭 시):**
```
제목: "🍽️ 오늘의 중식 메뉴 — 4개 매장 업데이트"
본문: "ABC식당, DEF레스토랑 외 2곳의 오늘 점심 메뉴를 확인하세요"
클릭 시: → DailyMenuListScreen (오늘의 메뉴 전용 화면)
```

**푸시 내용 (단일 발행 시 — 1곳만):**
```
제목: "🍽️ ABC식당 오늘의 중식"
본문: "쌀국수, 카레, 볶음밥"
클릭 시: → MerchantDetailScreen → 오늘의 메뉴 탭
```

**서버 구현:**
- SyncWorkers 크론: 매 5분마다 Redis 큐에서 끼니별 알림 집계
- 임직원별로 구독 가맹점의 미전송 메뉴 발행 건을 모아서 FCM 1건으로 배칭
- 배칭 후 큐에서 ack

### 19.11 알림 (구독 기반 — 오늘의 메뉴)

**핵심 원칙: 구독자에게만 전송**

```
가맹점이 DailyMenu 발행 (3끼 일괄)
    │
    ▼
CentralApi: 해당 branchId를 구독한 MealMerchantSubscription 목록 조회
    │
    ▼
끼니별 알림 설정 필터:
├── notifyBreakfast=true 인 구독자 → 조식 알림 큐
├── notifyLunch=true 인 구독자 → 중식 알림 큐
└── notifyDinner=true 인 구독자 → 석식 알림 큐
    │
    ▼
SyncWorkers: 각 큐를 알림 타이밍에 맞춰 FCM 전송
├── 조식: 전날 저녁 18:00 또는 당일 06:00
├── 중식: 당일 09:00 ~ 10:00
└── 석식: 당일 15:00 ~ 16:00
```

알림 유형 전체 목록:

| 이벤트 | 알림 제목 | 알림 본문 | 대상 | 타이밍 |
|--------|----------|----------|------|-------|
| `dailymenu.published` (조식) | 🌅 오늘의 조식 | "{구내식당} 오늘의 아침 메뉴가 등록되었습니다" | 조식 알림 ON 구독자 | 전날 18:00 또는 당일 06:00 |
| `dailymenu.published` (중식) | 🍱 오늘의 점심 | "{구내식당} 오늘의 점심 메뉴가 등록되었습니다" | 중식 알림 ON 구독자 | 당일 09:00~10:00 |
| `dailymenu.published` (석식) | 🌙 오늘의 저녁 | "{구내식당} 오늘의 저녁 메뉴가 등록되었습니다" | 석식 알림 ON 구독자 | 당일 15:00~16:00 |
| 마감 임박 | ⏰ 주문 마감 임박 | "{끼니} 사전주문 마감까지 30분" | 해당 끼니 구독자 중 미주문자 | 마감 30분 전 |
| `preorder.confirmed` | ✅ 주문 확정 | "{끼니} 사전주문 확정. 픽업: {시간}" | 주문자 본인 | 주문 직후 |

| `preorder.expired` | ⏰ 주문 만료 | "미수령으로 {끼니} 사전주문 만료" | 주문자 본인 | 픽업 슬롯 종료 후 |

### 19.12 백엔드 연동 (GraphQL)

#### 데이터 모델 변경

**DailyMenu** — 3끼 통합 모델:
```
DailyMenu: { id, branchId, menuDate, status, publishedAt, createdAt }
  (mealType 필드 없음 → DailyMenuItem에서 끼니 구분)

DailyMenuItem: { id, dailyMenuId, menuItemId,
  mealType: BREAKFAST | LUNCH | DINNER,    ← 끼니별 구분
  isSpecial, maxQuantity, sortOrder,
  preOrderDeadline: Timestamptz }          ← 끼니별 마감 시간
```

**MealMerchantSubscription (신규)**: §19.2 참조

**MealPreOrder 변경**:
```
├── ... (기존 필드)
├── mealType: BREAKFAST | LUNCH | DINNER   ← 끼니 유형 추가
└── Unique: (employeeId, dailyMenuId, mealType)  ← 1인 1끼니 1주문
```

#### Query

| Operation | 변수 | 반환 | 캐시 정책 |
|-----------|------|------|----------|
| `mealDailyMenuByBranch` | `branchId, date` | DailyMenu + items[] (3끼 포함) | `cache-and-network` |
| `mealDailyMenusForSubscribed` | `employeeId, date` | DailyMenu[] (구독 가맹점만) | `cache-and-network` |
| `mealMerchantSubscription` | `employeeId, branchId` | Subscription 상태 | `cache-first` |
| `mealMerchantSubscriptions` | `employeeId` | 내 구독 목록 전체 | `cache-and-network` |
| `mealPreOrdersByEmployee` | `employeeId, dateFrom?, dateTo?` | PreOrder[] (mealType 포함) | `cache-and-network` |
| `mealPreOrder` | `id` | PreOrder + items[] | `cache-first` |

#### Mutation

| Operation | Input | 반환 | 비고 |
|-----------|-------|------|------|
| `mealMerchantSubscribe` | `{ branchId }` | Subscription | 구독 생성/복원 |
| `mealMerchantUnsubscribe` | `{ branchId }` | Subscription | isActive → false |
| `mealMerchantSubscriptionUpdate` | `{ branchId, notifyBreakfast?, notifyLunch?, notifyDinner? }` | Subscription | 끼니별 알림 ON/OFF |
| `mealPreOrderCreate` | `{ dailyMenuId, mealType, items[{dailyMenuItemId, quantity}], pickupSlot }` | PreOrder | 끼니별 독립 주문 |
| `mealPreOrderCancel` | `{ id }` | PreOrder | 마감 전만 허용 |

#### Subscription (GraphQL-WS)

| Operation | 변수 | Payload | 용도 |
|-----------|------|---------|------|
| `mealDailyMenuPublished` | `employeeId` | `{ dailyMenuId, branchId, menuDate, mealTypes[], menuSummary[] }` | 구독 가맹점 메뉴 실시간 수신 |
| `mealPreOrderStatusChanged` | `preOrderId` | `{ id, status, mealType }` | 주문 상태 실시간 반영 |

#### 도메인 이벤트 → 앱 반응

| 이벤트 | 앱 동작 |
|--------|--------|
| `mealticket.dailymenu.published` | 홈 배너 갱신 (구독 가맹점만) |
| `mealticket.preorder.confirmed` | MyPreOrders 목록 갱신 + DailyMenu 탭 뱃지 |
| `mealticket.preorder.pickedup` | 결제 완료 알림 + 잔액 refetch |
| `mealticket.preorder.expired` | 만료 알림 + hold 해제 |

### 19.13 사전주문 결제 타이밍

일반 즉시 결제와 달리, 사전주문은 **수령 시점에 결제**가 발생한다. 끼니별 독립 주문이므로 hold도 끼니별로 독립.

```
중식 주문 확정          석식 주문 확정         중식 수령(픽업)
    │                      │                    │
    ▼                      ▼                    ▼
 중식 hold ₫140K      석식 hold ₫55K      중식 hold → 실결제
                                          (석식 hold 유지)
```

```
총 잔액: ₫ 2,500,000
├── 사용 가능:  ₫ 2,305,000
└── 사전주문 예약: ₫ 195,000  (2건)
    ├── 🍱 중식  ₫ 140,000
    └── 🌙 석식  ₫  55,000
```

### F.1 오프라인-온라인 잔액 동기화 (Race Condition)

**문제**: 구내식당 RFID 배지(오프라인) 결제 직후 → 도심 매장에서 앱(온라인) 결제 시도 → 잔액 불일치 가능.

**해결:**

| 계층 | 대응 |
|------|------|
| **POS (RFID)** | **온라인 필수**. POS도 서버 `mealTransactionAuthorize` 호출 후 승인. 네트워크 장애 시 결제 진입 차단 |
| **앱** | 앱 진입 시 `mealWallet` 쿼리 **강제 refetch** (`fetchPolicy: network-only`). 결제 직전에도 한 번 더 refetch |
| **서버** | `mealOrderCreate` (앱) / `mealTransactionAuthorize` (RFID) — 최종 잔액은 **서버 DB 기준** (앱 캐시 아님). 잔액 부족 시 `INSUFFICIENT_BALANCE` 거절 |
| **Subscription** | `mealWalletUpdated` — RFID 결제가 서버 반영되면 앱에 실시간 잔액 푸시 |

```
[구내식당 POS]                [CentralApi]              [앱]
    │                              │                      │
    │── RFID 결제 (오프라인) ──── │                      │
    │── Outbox 적재 ─────────── │                      │
    │                              │                      │
    │── 1분 후 동기화 ──────────>│                      │
    │                              │── Wallet 차감 ─────>│
    │                              │── Sub: walletUpdated ─>│ ← 잔액 갱신
    │                              │                      │
    │                              │<── 앱 결제 요청 ────│
    │                              │── 서버 DB 잔액 확인 ─│
    │                              │── 승인 or 거절 ────>│
```

### F.2 사전주문 No-show 정책

**문제**: 임직원이 사전주문 후 수령하지 않을 경우 (No-show) 가맹점은 음식을 준비했지만 손실 발생.

**핵심 원칙:**
> **가맹점은 주문을 수락한 시점에 해당 매출이 확정된다.** No-show가 발생해도 가맹점 정산금은 100% 보장.
> No-show에 대한 비용 처리는 **기업(회사) ↔ 임직원** 간 내부 문제로 처리한다.

#### F.2.1 자금 흐름 (No-show 시)

```
[임직원 지갑]                [플랫폼]                [가맹점]
     │                         │                       │
     │── 주문+결제 ──────────>│                       │
     │   (₫100K 차감)         │                       │
     │                         │── 주문 전달 ─────────>│
     │                         │<── 수락 ─────────────│
     │                         │                       │
     │  (No-show 발생)         │                       │
     │                         │                       │
     │                         │── 정산금 ₫100K ─────>│ ← 가맹점은 100% 수령 (확정)
     │                         │   (수수료 차감 후)     │
     │                         │                       │
     │<── 페널티 처리 ────────│                       │
     │   (기업 정책에 따라      │                       │
     │    환불 0~100%)         │                       │
```

**핵심:** 가맹점 입장에서는 주문 수락 = 매출 확정. No-show 여부와 관계없이 정산금을 받는다.

#### F.2.2 No-show 확인 주체 및 절차

| 단계 | 주체 | 행동 | 시스템 처리 |
|------|------|------|------------|
| 1 | **시스템 (자동)** | `READY` 상태에서 유예 시간(기본 30분) 초과 + `COMPLETED` 미전환 | 자동으로 `NO_SHOW` 후보 마킹 |
| 2 | **가맹점 (POS)** | POS에 "미수령 확인" 알림 표시 → 매장 직원이 **[미수령 확정]** 버튼 클릭 | `NO_SHOW_CONFIRMED` 상태 전환 |
| 3 | **임직원 (앱)** | 앱에 "수령하셨나요?" 푸시 알림 → **[수령 완료]** 또는 **무응답** | 수령 클릭 시 `COMPLETED`, 무응답 시 No-show 유지 |
| 4 | **시스템 (자동)** | 가맹점 확정 OR 유예 시간+추가 30분 경과 시 최종 `NO_SHOW` 처리 | 페널티 정책 적용 |

**확인 우선순위:** 가맹점(POS) 확인 > 임직원(앱) 응답 > 시스템 자동

```
READY
  ↓ (유예 시간 초과)
NO_SHOW_PENDING  ← 시스템 자동 마킹
  ├── 가맹점 [미수령 확정] → NO_SHOW_CONFIRMED → 페널티 처리
  ├── 임직원 [수령 완료]  → COMPLETED (정상 종결)
  └── 추가 30분 무응답    → NO_SHOW_CONFIRMED → 페널티 처리 (자동)
```

#### F.2.3 페널티 정책 (기업 ↔ 임직원)

| 정책 필드 | 위치 | 설명 |
|-----------|------|------|
| `noShowPenaltyRatio` | `MealPolicy.ruleJson` | 0.0~1.0 — 임직원 지갑에서 차감할 비율 (1.0 = 전액 임직원 부담, 0 = 기업 부담) |
| `noShowGracePeriodMin` | `MealPolicy.ruleJson` | 수령 마감 후 유예 시간 (분) — 기본 30분 |
| `noShowMaxMonthly` | `MealPolicy.ruleJson` | 월간 No-show 허용 횟수 (초과 시 사전주문 차단) |
| `noShowCompanyAbsorb` | `MealPolicy.ruleJson` | true = 기업이 No-show 비용 전액 흡수 (복리후생 차원) |

**시나리오별 처리:**

| 시나리오 | 기업 정책 | 임직원 지갑 처리 | 가맹점 |
|---------|----------|----------------|--------|
| A. 기업 전액 흡수 | `noShowCompanyAbsorb: true` | 환불 없음 (이미 차감됨). 기업이 복리후생 비용으로 처리 | **100% 정산** |
| B. 임직원 100% 페널티 | `penaltyRatio: 1.0` | 환불 없음 — 전액 임직원 부담 | **100% 정산** |
| C. 50:50 분담 | `penaltyRatio: 0.5` | 50% 환불 (개인충전 bucket 우선 환불) — 나머지 50%는 임직원 페널티 | **100% 정산** |
| D. 임직원 면책 | `penaltyRatio: 0.0` | 전액 환불 — 기업이 100% 부담 | **100% 정산** |

> **모든 시나리오에서 가맹점 정산금은 100%.** 페널티 비율은 오직 기업 ↔ 임직원 간 비용 분담 비율.

#### F.2.4 CorporatePortal 설정 (정책 빌더)

```
┌──────────────────────────────────────┐
│ 📋 No-show 정책                      │
├──────────────────────────────────────┤
│                                      │
│  기업 전액 흡수                       │
│  [○ OFF  ● ON]                       │  ← ON 시 아래 설정 비활성화
│                                      │
│  임직원 페널티 비율                    │
│  ────────●────────── 50%             │  ← 슬라이더 0~100%
│  (0% = 기업 부담, 100% = 임직원 부담) │
│                                      │
│  수령 유예 시간                        │
│  [30] 분                              │  ← 10~120분
│                                      │
│  월간 No-show 허용 횟수               │
│  [3] 회                               │  ← 초과 시 사전주문 차단
│  (초과 시 해당 월 사전주문 기능 비활성화) │
│                                      │
└──────────────────────────────────────┘
```

#### F.2.5 구현 요구사항

**주문 상태 머신 확장:**
```
기존: READY → COMPLETED
추가: READY → NO_SHOW_PENDING → NO_SHOW_CONFIRMED
                              → COMPLETED (뒤늦게 수령)
```

**DB:**
- `MealOrder.status`에 `NO_SHOW_PENDING`, `NO_SHOW_CONFIRMED` 추가
- `MealOrder.noShowConfirmedBy` (가맹점 직원 or SYSTEM)
- `MealOrder.noShowConfirmedAt`
- `MealOrder.noShowPenaltyVnd` (실제 페널티 차감 금액)

**서비스:**
- 크론 (매분): `WHERE status = 'READY' AND readyAt + gracePeriod < NOW()` → `NO_SHOW_PENDING`
- 크론 (매분): `WHERE status = 'NO_SHOW_PENDING' AND noShowPendingAt + 30min < NOW()` → `NO_SHOW_CONFIRMED` (자동)
- `mealOrderConfirmNoShow(orderId)` — POS mutation (가맹점 직접 확인)
- `mealOrderLatePickup(orderId)` — 앱 mutation (뒤늦은 수령 확인)
- No-show 확정 시: 페널티 비율에 따라 부분 환불 → AuditLog `ORDER_NO_SHOW`

**알림:**
- 임직원 앱: "주문 #A-042를 수령하셨나요?" 푸시 (유예 시간 초과 시)
- POS: "미수령 주문이 있습니다 — 확인해주세요" 팝업
- CorporatePortal: 월간 No-show 리포트 (임직원별 횟수)

### F.3 GPS 검증 한계 보완

**문제**: 대형 쇼핑몰(Landmark 81), 고층 빌딩 등 실내 GPS 오차 심함 (50m~200m).

**보완 전략 (단계별):**

| 단계 | 방식 | 정확도 | 비용 |
|------|------|--------|------|
| **Phase 1** (기본) | GPS 반경 확대 (실내 식당: 1km) | 낮음 | 무료 |
| **Phase 1** (Fallback) | **가맹점 QR 스캔** — 매장 입구에 고정 QR 게시, 앱으로 스캔 시 위치 인증 | 높음 | 무료 |
| **Phase 2** | Wi-Fi fingerprinting — 건물 내 Wi-Fi AP MAC 기반 위치 추정 | 중간 | 낮음 |
| **Phase 3** | BLE Beacon — 가맹점에 Bluetooth Beacon 설치, 앱 진입 감지 | 높음 | Beacon 비용 |

**Phase 1 Fallback QR 구현:**
```
가맹점 QR: vmeal://checkin/{branchId}/{verificationCode}
→ 앱에서 스캔 → 서버 검증 (branchId + code 유효성)
→ 10분간 해당 branchId에서 결제 허용 (GPS 검증 생략)
```

- `MealOrder.createInput`에 `checkinToken?: String` 추가
- 서버: checkinToken 유효 시 GPS 검증 건너뜀
- 가맹점 QR: SuperAdmin Portal에서 branchId별 고유 코드 생성, 인쇄용 PDF 다운로드 제공

**DB 확장:**
```prisma
model MealCheckinToken {
  id          String   @id @default(uuid()) @db.Uuid
  branchId    String   @db.Uuid
  code        String   @unique @db.VarChar(60) // 랜덤 고유 코드
  isActive    Boolean  @default(true)
  createdAt   DateTime @default(now()) @db.Timestamptz()
  
  @@index([branchId, isActive])
}
```

### F.4 POS 주문 알림 강도 — `⚙️ 백엔드 선행 구현 (POS 프론트 미시작)`

**문제**: 매장 주인이 주문을 놓치면 타임아웃 → 자동 취소 → 매출 손실.

**해결: 강력한 POS 알림 메커니즘**

| 알림 수단 | 트리거 | 설명 |
|-----------|--------|------|
| **화면 팝업** | 새 주문 수신 | 전체 화면 오버레이, 주문 내용 표시 |
| **오디오 알림** | 새 주문 수신 | 반복 알림음 (30초 간격, 수락/거절까지) |
| **진동** | 새 주문 수신 | 태블릿/모바일 POS 진동 |
| **반복 알림** | 미응답 2분 | "미확인 주문이 있습니다" 재알림 (더 강한 알림음) |
| **SMS/Push** | 미응답 5분 | 매장 담당자 휴대폰으로 SMS/Push 발송 |
| **에스컬레이션** | 미응답 8분 | SuperAdmin 대시보드에 경고 표시 |

**POS 앱 (BrandPosApp) 구현:**
- GraphQL Subscription `mealOrderReceived` 수신 시 → `SoundPlayer.play('new-order.mp3')` + 전체 화면 팝업
- 팝업: [수락 ✅] [거절 ❌] 버튼 + 자동 스크롤되는 주문 항목
- 수락/거절 전까지 팝업 닫기 불가 (모달 lock)
- 알림음: 30초 간격 반복 (`setInterval` + `AppState` 감시)
