## 1. 전체 자금 흐름도

```
┌─────────────┐    ①예치금/크레딧     ┌──────────────┐    ②지원금 배정     ┌──────────────┐
│  기업 고객   │ ─────────────────→ │  플랫폼(SA)   │ ─────────────→ │  임직원 지갑  │
│ (Corporate) │ ←─────────────────  │  수탁 계좌    │                │  (MealWallet) │
│             │    세금계산서 발행   │              │                │              │
└─────────────┘                    └──────┬───────┘                └──────┬───────┘
                                          │                               │
                                          │ ④수수료 공제                    │ ③식권 결제
                                          │ + 정산금 지급                   │ (RFID/QR)
                                          │                               ▼
                                   ┌──────▼───────┐              ┌──────────────┐
                                   │  가맹점 정산  │ ←──────────  │  가맹점 POS  │
                                   │  계좌 (Bank) │   매출 집계   │  (BrandHQ)   │
                                   └──────────────┘              └──────────────┘
```

### 자금 흐름 4단계

| 단계 | 출발 | 도착 | 트리거 | 금액 결정 |
|------|------|------|--------|-----------|
| ① 예치금/크레딧 입금 | 기업 고객 | 플랫폼 수탁 계좌 | 기업 관리자 입금 확인 | `MealFundingAccount.depositBalanceVnd` |
| ② 지원금 배정 | 플랫폼 | 임직원 지갑 | 기업 관리자 일괄 충전 | `MealWalletFundingEntry.amountVnd` |
| ③ 식권 결제 | 임직원 지갑 | 가맹점 매출 | POS RFID/QR 태그 | `MealTransaction.approvedAmountVnd` |
| ④ 정산 지급 | 플랫폼 | 가맹점 은행 | 월말 정산 배치 | `netPayableVnd = gross - commission` |

## 2. 플랫폼별 기능 상세

### 2.1 SuperAdmin Portal (`localhost:3001`)

SuperAdmin은 **플랫폼 전체의 자금 흐름을 총괄**한다.

#### 2.1.1 기업 고객 결제 관리 (Corporate → Platform)

**기능 목록:**

| 기능 | 설명 | 구현 상태 |
|------|------|-----------|
| 예치금 입금 확인 | 기업의 은행 이체 확인 후 `depositBalanceVnd` 증액 | ⚠️ 수동 (API만 존재) |
| 크레딧 한도 설정 | CREDIT_NET15/NET30 기업의 신용 한도 설정 | ✅ 구현 완료 |
| 예치금 잔액 모니터링 | 기업별 예치금 잔액 대시보드 | ❌ 미구현 |
| 연체 관리 | 크레딧 기업의 미결제 경고/정지 | ❌ 미구현 |
| 입금 내역 원장 | 기업별 입출금 이력 조회 | ⚠️ 부분 (FundingEntry만) |
| 청구서 발행 | 크레딧 기업 대상 월말 청구서 | ❌ 미구현 |
| 자동 입금 매칭 | 은행 입금 → 기업 계정 자동 매칭 (가상계좌) | ❌ 미구현 |

**워크플로우: 예치금 입금 확인**
```
1. 기업 → 플랫폼 수탁 은행계좌로 이체
2. 은행 → Webhook/배치로 입금 알림 수신 (Phase 2)
   또는 SuperAdmin → 수동 입금 확인 (Phase 1)
3. SuperAdmin Portal → "입금 확인" 버튼 클릭
4. CentralApi → MealFundingAccount.depositBalanceVnd += 입금액
5. CentralApi → AuditLog 기록 (actionType: DEPOSIT_CONFIRMED)
6. CorporatePortal → 예치금 잔액 실시간 반영
```

**워크플로우: 크레딧 청구/결제**
```
1. 월말 → 크레딧 기업의 당월 사용 총액 집계
2. SuperAdmin → 청구서 생성 (사용액 + 수수료 = 청구 총액)
3. 청구서 → 기업 관리자에게 이메일/포털 알림
4. 기업 → 은행 이체로 청구액 납부 (NET15/NET30 기한)
5. 입금 확인 → creditOutstandingVnd 감소
6. 미납 시 → 경고 → 정지 (newTransaction 차단)
```

#### 2.1.2 가맹점 정산 관리 (Platform → Merchant)

**기능 목록:**

| 기능 | 설명 | 구현 상태 |
|------|------|-----------|
| 정산 배치 실행 | 기간별 3-Way Matching 실행 | ✅ 구현 완료 |
| 정산 예외 처리 | EXCEPTION 건 수동 검토/해결 | ❌ 미구현 |
| 정산 승인 | MATCHED → 지급 승인 워크플로우 | ❌ 미구현 |
| 은행 이체 실행 | 승인된 정산금 은행 이체 요청 | ❌ 미구현 |
| 이체 결과 확인 | 은행 이체 ACK → PAID 마킹 | ✅ 구현 완료 (markPaid) |
| 수수료율 관리 | 가맹점별 수수료율 설정/이력 | ✅ 구현 완료 |
| 정산 리포트 | 기간별/가맹점별 정산 요약 | ❌ 미구현 |
| 정산 대시보드 | 미정산/예외/완료 현황 총괄 | ❌ 미구현 |

**워크플로우: 월말 정산**
```
1. 매월 1일 (또는 수동) → Settlement Batch 실행
   - 전월 APPROVED 트랜잭션 집계
   - 기업 원장 vs POS 거래 3-Way Matching
   - 수수료 계산 (baseRatePct 적용)
2. MATCHED → SuperAdmin 검토 큐에 진입
3. EXCEPTION → SuperAdmin 예외 처리 화면
   - 불일치 내역 확인
   - 수동 조정/재매칭/거절
4. 정산 승인 → "지급 승인" 버튼
5. 은행 이체 요청
   - Phase 1: 수동 이체 후 이체 확인서 업로드
   - Phase 2: 은행 API 연동 자동 이체
6. 이체 완료 → markPaid → PAID 상태
7. 정산 완료 알림 → 가맹점 관리자
```

**수수료 구조:**

| 수수료 타입 | 필드 | 적용 방식 |
|------------|------|----------|
| 기본 수수료 | `baseRatePct` (%) | `grossAmount × rate / 100` |
| 특수 지역 수수료 | `specialZoneRatePct` (%) | 특수 구역 가맹점 적용 (선택) |
| 프랜차이즈 정액 | `franchiseFlatRatePct` (%) | 프랜차이즈 본사 일괄 (선택) |
| **플랫폼 서비스 수수료** | **미구현** | **기업 대상 월정액 또는 거래 %** |

|-------------------|------------------|-------------|

#### 2.1.4 수익 대시보드 (신규)

**필요 위젯:**

| 위젯 | 데이터 소스 | 설명 |
|------|-----------|------|
| 월간 거래 총액 | `SUM(MealTransaction.approvedAmountVnd)` | 전체 플랫폼 거래량 |
| 월간 수수료 수익 | `SUM(MealSettlementBatch.commissionAmountVnd)` | 가맹점 수수료 합계 |
| 미정산 금액 | `SUM(netPayableVnd) WHERE status != PAID` | 아직 지급하지 않은 정산금 |
| 기업 미수금 | `SUM(creditOutstandingVnd)` | 크레딧 기업 미납 합계 |
| 예치금 총액 | `SUM(depositBalanceVnd)` | 수탁 예치금 총합 |
| 인보이스 현황 | `COUNT BY status` | DRAFT/REQUESTED/ACCEPTED 파이 차트 |
| 가맹점별 매출 Top 10 | `GROUP BY brandHqId` | 매출 상위 가맹점 |
| 기업별 사용량 Top 10 | `GROUP BY corporateId` | 사용량 상위 기업 |

## 3. 결제 수단 상세

### 3.1 기업 → 플랫폼 결제

| 결제 수단 | 설명 | 우선순위 | 구현 상태 |
|-----------|------|---------|-----------|
| **은행 이체** | 기업 → 플랫폼 수탁 계좌 직접 이체 | P0 | ⚠️ 수동 확인 |

## 4. 주요 비즈니스 로직

### 4.1 Split Payment (분할 결제) 로직

```
입력: requestedAmountVnd, wallet { companyAllowanceVnd, personalTopUpVnd, balanceVnd }
규칙: 회사 지원금 우선 사용 → 부족분은 개인 충전에서 차감

if (policy.allowSplitPayment == false) {
  // 회사 지원금만으로 결제 가능해야 함
  if (requestedAmount > companyAllowanceVnd) → DECLINE (SPLIT_PAYMENT_DISABLED)
  companyShare = requestedAmount
  employeeShare = 0
} else {
  // 회사 지원금 우선 차감, 부족분 개인 충전
  companyShare = min(requestedAmount, companyAllowanceVnd)
  employeeShare = requestedAmount - companyShare
  if (employeeShare > personalTopUpVnd) → DECLINE (INSUFFICIENT_BALANCE)
}
```

### 4.2 3-Way Matching (정산 매칭) 로직

```
매칭 대상 3축:
  A. POS 거래 합산 (grossAmountVnd = SUM(approvedAmountVnd))
  B. 기업 원장 (companyShareTotal = SUM(companyShareVnd))
  C. 기업 충전 원장 (corporateLedgerTotal = SUM(fundingEntry.amountVnd))

매칭 판정:
  if (B != C) → threeWayMismatchCount = 1 → status = EXCEPTION
  else → threeWayMismatchCount = 0 → status = MATCHED

정산금 계산:
  commissionAmountVnd = grossAmountVnd × baseRatePct / 100
  netPayableVnd = grossAmountVnd - commissionAmountVnd

정산 후:
  - 매칭된 트랜잭션: status → SETTLED, settledAt = now()
  - 배치: status → MATCHED (검토 대기) 또는 EXCEPTION (수동 처리)
```

### 4.3 예치금 잔액 검증 로직

```
기업 Funding Model 에 따라:

PREPAID_DEPOSIT:
  충전 요청 시: depositBalanceVnd >= 충전 총액 검증
  충전 실행 시: depositBalanceVnd -= 충전 총액

CREDIT_NET15 / CREDIT_NET30:
  충전 요청 시: (creditLimitVnd - creditOutstandingVnd) >= 충전 총액 검증
  충전 실행 시: creditOutstandingVnd += 충전 총액
  청구 납부 시: creditOutstandingVnd -= 납부액
```

### 4.4 전자세금계산서 생성 로직

```
generate(corporateId, periodStart, periodEnd):
  1. 기간 내 SETTLED 트랜잭션 집계
  2. consolidationStrategy 에 따라 라인 그룹화:
     - BY_MERCHANT: 가맹점별 1 라인
     - BY_DAY: 일별 1 라인
     - BY_DEPARTMENT: 부서별 1 라인
     - SINGLE_LINE: 전체 1 라인
  3. 각 라인: amountVnd, vatAmountVnd(10%), payAmountVnd
  4. Seller: PlatformLegalEntity (findActive())
  5. Buyer: MealCorporate (taxCode, companyName, addressFull)
  6. Status: DRAFT → 기업 검토 대기
```

## 8. 결제 상태 머신

### 8.1 기업 결제 상태

```
UNPAID → PAYMENT_REQUESTED → PAYMENT_CONFIRMED → PAID
                           → PAYMENT_FAILED
PAID → (다음 청구 주기) → UNPAID
```

### 8.2 정산 배치 상태

> **현재 스키마**: `OPEN | MATCHING | MATCHED | EXCEPTION | PAID`
> **확장 필요**: `APPROVED`, `PAYOUT_REQUESTED`, `RESOLVED`, `WRITTEN_OFF` 추가

```
OPEN → MATCHING → MATCHED → APPROVED → PAYOUT_REQUESTED → PAID
                → EXCEPTION → RESOLVED → MATCHED (재매칭)
                            → WRITTEN_OFF (손실 처리)
```

**스키마 마이그레이션 필요:**
```sql
-- MealSettlementBatch.status 확장 (기존 5개 + 신규 4개)
-- OPEN | MATCHING | MATCHED | EXCEPTION | PAID | APPROVED | PAYOUT_REQUESTED | RESOLVED | WRITTEN_OFF
```

### 8.3 전자세금계산서 상태

```
(생성) → DRAFT → REQUESTED → SUBMITTING → ACCEPTED
              → DISPUTED                → REJECTED → (재발행)
ACCEPTED → VOIDED (취소)
```

### 9.1 법적 근거

| 법령 | 관련 조항 | 적용 |

**핵심 법률 요건:**
- 상업 계약은 **서면** 필수 (Art. 400: 당사자 정보, 계약 대상, 대금, 결제 조건, 권리·의무)

| 플랫폼 액션 | 계약 요청서 접수 → `Contract` 레코드 생성 |
| 기록 | 요청자, 요청일, 계약 유형, 상대방 정보 |
| 알림 | SuperAdmin에게 신규 계약 요청 알림 |

**진행 이력 예시:**
```
[2026-04-13 09:00] 계약 요청 접수 — 요청자: 김기업 (기업관리자)
                   계약 유형: CORPORATE (식권고객사 서비스 계약)
                   상대방: ABC 기업 (taxCode: 0312345678)
```

#### 단계 2: 초안 작성 (`DRAFT`)

| 항목 | 내용 |
|------|------|
| 담당자 | SuperAdmin |
| 액션 | 템플릿 선택 → 웹 에디터에서 3개 언어(vi/ko/en) 원문 작성 |
| 자동 채우기 | 상대방 정보 (법인명, 세금코드, 대표자, 주소), 계약 조건 (수수료율, 한도) |
| 산출물 | 계약서 원문 (bodyJson) + 조건 구조화 데이터 (termsJson) |
| 알림 | 없음 (내부 작업) |

**진행 이력 예시:**
```
[2026-04-13 10:30] 초안 작성 시작 — 작성자: 이운영 (SuperAdmin)
                   템플릿: CORPORATE_SERVICE_V3
[2026-04-13 14:00] 초안 작성 완료 — 3개 언어 원문 + 조건 입력 완료
                   내부 검토 요청 발송
```

#### 단계 3: 내부 검토/승인 (`INTERNAL_REVIEW`)

| 항목 | 내용 |
|------|------|
| 담당자 | SuperAdmin 법무/재무 담당 |
| 액션 | 계약서 원문 검토 + 조건 적정성 확인 |
| 검토 항목 | 법적 조항 적합성, 수수료율 적정성, 리스크 평가 |
| 승인 방식 | 단독 승인 (일반) 또는 2인 승인 (고액 계약) |
| 알림 | 승인 요청 → 검토자에게 이메일 + 포털 알림 |

**진행 이력 예시:**
```
[2026-04-13 14:05] 내부 검토 요청 — 검토자: 박법무 (SuperAdmin)
[2026-04-13 16:00] 내부 검토 승인 — 승인자: 박법무
                   코멘트: "수수료율 5% → 4.5%로 조정 권고"
[2026-04-13 16:30] 조건 수정 반영 — 작성자: 이운영
                   baseRatePct: 5.00 → 4.50
```

#### 단계 4: 고객사 발송/전달 (`SENT_TO_PARTY`)

| 항목 | 내용 |
|------|------|
| 담당자 | SuperAdmin |
| 액션 | 승인된 초안을 상대방 포털에 전달 + 이메일 발송 |
| 발송 수단 | ① 포털 내 알림 (계약 상세 페이지 링크) ② 이메일 (PDF 첨부) |
| 기한 | 검토 회신 기한 설정 (기본 7영업일) |
| 알림 | 상대방 관리자에게 이메일 + 포털 알림 |

**이메일 내용:**
```
제목: [식권플랫폼] 서비스 계약서 검토 요청 — ABC 기업
본문: 안녕하세요, ABC 기업 담당자님.
      첨부된 계약서 초안을 검토해 주시기 바랍니다.
      검토 기한: 2026-04-20
      포털에서 직접 검토/수정: [링크]
첨부: contract_ABC_v1_ko.pdf, contract_ABC_v1_vi.pdf
```

**진행 이력 예시:**
```
[2026-04-14 09:00] 고객사 발송 — 수신자: 김기업 (ABC 기업 관리자)
                   발송 수단: 이메일 + 포털 알림
                   검토 기한: 2026-04-20
                   첨부: PDF 2부 (ko, vi)
```

#### 단계 5: 협상/수정 (`NEGOTIATING`)

| 항목 | 내용 |
|------|------|
| 담당자 | 양사 |
| 액션 | 상대방이 검토 후 수정 요청 또는 동의 |
| 수정 방식 | 웹 에디터에서 조항 수정 → `ContractRevision` 자동 생성 |
| 수정 이력 | 변경 전/후 값, 수정자, 수정 사유, 언어(locale) 기록 |
| 알림 | 수정 발생 시 상대방에게 즉시 이메일 + 포털 알림 |
| 반복 | 양사 수정 → 확인 → 재수정 → 확인 (합의까지 반복) |
| 타임아웃 | 미확인 수정은 48시간 후 자동 리마인더 |

**수정 알림 예시:**
```
제목: [식권플랫폼] 계약서 수정 알림 — ABC 기업
본문: ABC 기업 담당자가 다음 항목을 수정했습니다:
      수정 항목: 제4조 (정산 주기)
      변경 전: "매월 10일까지"
      변경 후: "매월 15일까지"
      사유: "회계 마감일 맞춤"
      [포털에서 확인하기]
```

**진행 이력 예시:**
```
[2026-04-16 11:00] 수정 요청 — 수정자: 김기업 (ABC 기업)
                   항목: termsJson.settlementDay (10 → 15)
                   사유: "회계 마감일 맞춤"
[2026-04-16 14:00] 수정 확인 — 확인자: 이운영 (SuperAdmin)
                   결과: 동의
[2026-04-16 14:30] 양사 합의 완료 → 상태: AGREED
```

**상태: `NEGOTIATING` → 양사 동의 시 `AGREED`**

#### 단계 6: 서명/날인 (`SIGNING`)

| 항목 | 내용 |
|------|------|
| 담당자 | 양사 대표 또는 위임자 |
| 액션 (Phase 1) | 합의본 Word/PDF 다운로드 → 인쇄 2부 → 서명/날인 |
| 액션 (Phase 2) | CA 디지털 서명 (전자거래법 2023) |
| 서명 순서 | ① 플랫폼 먼저 서명 → ② 상대방 서명 |
| 알림 | 서명 요청 → 상대방에게 이메일 (서명 안내 + 다운로드 링크) |

**서명 요청 이메일:**
```
제목: [식권플랫폼] 계약서 서명 요청 — ABC 기업
본문: 합의된 계약서를 첨부합니다.
      1. 첨부 파일을 인쇄하여 2부 서명/날인해 주세요
      2. 1부는 귀사 보관, 1부는 당사에 회신해 주세요
      3. 서명된 원본의 스캔본을 포털에 업로드해 주세요
      서명 기한: 2026-04-25
      [Word 다운로드 (한국어)] [Word 다운로드 (베트남어)]
```

**진행 이력 예시:**
```
[2026-04-17 09:00] 서명 요청 발송 — 수신자: 김기업
                   첨부: Word 2부 (ko, vi)
                   서명 기한: 2026-04-25
[2026-04-17 10:00] 플랫폼 서명 완료 — 서명자: 박대표 (플랫폼 법인)
                   스캔본 업로드: signed_party_a_ko.pdf, signed_party_a_vi.pdf
```

**상태: `AGREED` → `PENDING_SIGNATURE` → 양사 서명 완료 시 `SIGNED`**

#### 단계 7: 원본 교환 및 스캔본 등록 (`EXCHANGING`)

| 항목 | 내용 |
|------|------|
| 담당자 | 양사 |
| 물리 교환 | 서명된 원본 1부를 상대방에게 전달 (우편/직접) |
| 스캔본 등록 | 양사 각각 서명 완본 스캔 → 포털에 업로드 (언어별) |
| 검증 | SuperAdmin이 스캔본 확인 (서명/날인 유무, 원본 일치 여부) |
| 알림 | 스캔본 등록 시 상대방에게 알림 |

**업로드 규칙:**
- 언어별 각각 업로드 (ko/vi 별도 스캔)
- 파일 형식: PDF (스캔) — 최대 50MB
- 양사 모두 업로드 완료 + SuperAdmin 확인 → 계약 활성화

**진행 이력 예시:**
```
[2026-04-20 14:00] 상대방 서명 완료 — 서명자: 김대표 (ABC 기업)
                   스캔본 업로드: signed_party_b_ko.pdf, signed_party_b_vi.pdf
[2026-04-20 15:00] 원본 교환 확인 — 확인자: 이운영 (SuperAdmin)
                   양사 서명 완본 확인 → 계약 활성화
[2026-04-20 15:05] 계약 활성화 — effectiveFrom: 2026-05-01
                   상태: SIGNED → ACTIVE
```

**상태: `SIGNED` → 양사 스캔본 등록 + SuperAdmin 확인 → `ACTIVE`**

#### 단계 8: 이행 및 관리 (`ACTIVE`)

| 항목 | 내용 |
|------|------|
| 관리 항목 | 계약 이행 모니터링, 갱신/해지 관리 |
| 만료 알림 | 90일 전 / 30일 전 / 7일 전 자동 알림 |
| 갱신 | 갱신 시 `parentContractId` 참조 + 신규 버전 생성 |
| 변경 | 조건 변경 시 변경 계약서 (부속 합의서) 별도 생성 |
| 해지 | 사유 기록 + 해지 통보서 발송 |
| 조회 | 양사 모두 언제든 원문 웹 열람 + Word/PDF/스캔본 다운로드 |

**상태: `ACTIVE` → `EXPIRING` (만료 90일 전) → `RENEWED` / `TERMINATED`**

### 9.4 계약 상태 머신

> 상태값은 UPPER_SNAKE_CASE (CLAUDE.md 디스크리미네이터 규칙)

```
REQUESTED → DRAFT → INTERNAL_REVIEW → SENT_TO_PARTY → NEGOTIATING → AGREED
                                                                         ↓
               CANCELLED ← ──────────────────────────────── NEGOTIATING
                                                                         ↓
                                                          PENDING_SIGNATURE
                                                                         ↓
                                                               SIGNING
                                                                         ↓
                                                              EXCHANGING
                                                                         ↓
                                                                ACTIVE
                                                                ↓     ↓
                                                          EXPIRING  SUSPENDED
                                                          ↓     ↓        ↓
                                                     RENEWED  TERMINATED TERMINATED
```

**상태값 목록 (14개):**

| 상태 | 설명 | 다음 가능 상태 |
|------|------|---------------|
| `REQUESTED` | 계약 요청 접수 | → `DRAFT` |
| `DRAFT` | 초안 작성 중 | → `INTERNAL_REVIEW` |
| `INTERNAL_REVIEW` | 내부 법무/재무 검토 | → `SENT_TO_PARTY`, → `DRAFT` (반려) |
| `SENT_TO_PARTY` | 고객사에 전달 | → `NEGOTIATING` |
| `NEGOTIATING` | 협상/수정 진행 중 | → `AGREED`, → `CANCELLED` |
| `AGREED` | 양사 합의 완료 | → `PENDING_SIGNATURE` |
| `PENDING_SIGNATURE` | 서명 대기 | → `SIGNING` |
| `SIGNING` | 서명/날인 진행 중 | → `EXCHANGING` |
| `EXCHANGING` | 원본 교환 + 스캔본 등록 중 | → `ACTIVE` |
| `ACTIVE` | 이행 중 (활성) | → `EXPIRING`, → `SUSPENDED`, → `TERMINATED` |
| `EXPIRING` | 만료 임박 (90일 전) | → `RENEWED`, → `TERMINATED` |
| `RENEWED` | 갱신 완료 (신규 버전 DRAFT 생성) | 종결 |
| `SUSPENDED` | 위반/분쟁으로 일시 정지 | → `ACTIVE` (해제), → `TERMINATED` |
| `TERMINATED` | 해지/만료 종결 | 종결 |
| `CANCELLED` | 협상 결렬 취소 | 종결 |

### 9.4.1 계약 진행 이력 (ContractActivity)

모든 상태 전이와 주요 액션을 시간순으로 기록하는 활동 로그.

```prisma
model ContractActivity {
  id           String   @id @default(uuid()) @db.Uuid
  contractId   String   @db.Uuid
  activityType String   @db.VarChar(50)   // STATUS_CHANGED | REVISION_CREATED | FILE_UPLOADED |
                                           // EMAIL_SENT | REVIEW_REQUESTED | REVIEW_APPROVED |
                                           // SIGNATURE_REQUESTED | SIGNATURE_COMPLETED |
                                           // SCAN_UPLOADED | EXCHANGE_CONFIRMED | RENEWAL_TRIGGERED
  fromStatus   String?  @db.VarChar(30)   // 이전 상태 (STATUS_CHANGED 시)
  toStatus     String?  @db.VarChar(30)   // 이후 상태
  actorId      String   @db.Uuid          // 수행자
  actorType    String   @db.VarChar(30)   // SUPER_ADMIN | BRAND_ADMIN | CORPORATE_ADMIN | SYSTEM
  summary      String   @db.VarChar(500)  // 사람이 읽을 수 있는 요약 (vi/ko/en)
  summaryKo    String?  @db.VarChar(500)
  summaryEn    String?  @db.VarChar(500)
  metadata     Json?                      // 추가 데이터 (파일명, 이메일 주소, 수정 항목 등)
  createdAt    DateTime @default(now()) @db.Timestamptz()

  contract Contract @relation(fields: [contractId], references: [id])

  @@index([contractId, createdAt(sort: Desc)])
  @@index([actorId, actorType])
}
```

**UI 표시 (타임라인):**
```
📋 2026-04-13 09:00  계약 요청 접수       김기업 (기업관리자)
📝 2026-04-13 14:00  초안 작성 완료       이운영 (SuperAdmin)
🔍 2026-04-13 16:00  내부 검토 승인       박법무 (SuperAdmin)
📤 2026-04-14 09:00  고객사 발송          이운영 (SuperAdmin) → 이메일 발송
✏️ 2026-04-16 11:00  수정 요청            김기업 — 정산 주기 10일→15일
✅ 2026-04-16 14:30  양사 합의            자동 — 모든 수정 확인 완료
📩 2026-04-17 09:00  서명 요청 발송       이운영 → Word 첨부
🖊️ 2026-04-17 10:00  플랫폼 서명 완료    박대표 — 스캔본 2부 업로드
🖊️ 2026-04-20 14:00  상대방 서명 완료    김대표 — 스캔본 2부 업로드
📦 2026-04-20 15:00  원본 교환 확인       이운영 — 양사 완본 검증

```

### 9.5 수정 이력 추적 (Revision Tracking)

```
ContractRevision {
  id, contractId, revisionNo,
  modifiedBy      // 수정자 (userId + userType)
  modifiedAt      // 수정 시점
  changeType      // CLAUSE_EDIT | TERM_CHANGE | AMOUNT_CHANGE
  fieldPath       // 변경된 필드 경로 (예: "commissionRate.baseRatePct")
  beforeValue     // 변경 전 값 (JSON)
  afterValue      // 변경 후 값 (JSON)
  reason          // 수정 사유
  ackBy           // 상대방 확인자
  ackAt           // 상대방 확인 시점
}
```

**수정 알림 규칙:**
- 수정 발생 → 상대방에게 즉시 이메일 + 포털 내 알림
- 알림 내용: 수정 항목, 변경 전/후 값, 수정 사유
- 상대방은 "확인" 또는 "추가 수정 요청" 선택
- 미확인 수정은 48시간 후 자동 리마인더

### 9.6 계약서 원문 작성 및 저장

#### 원문 작성 방식

계약서 원문은 **웹 에디터에서 직접 작성**하여 DB에 저장한다.

```
[웹 에디터(Rich Text)] → [구조화 JSON + HTML Text] → [DB 저장 (3개 언어)]
                                                    → [Word(.docx) 다운로드]
                                                    → [PDF 미리보기]
```

**에디터 기술:** TipTap (ProseMirror 기반) 또는 Lexical — HTML 출력 + JSON 구조 동시 저장

#### 다국어 저장 구조

계약서 원문은 **베트남어(vi), 한국어(ko), 영어(en) 3개 언어를 각각 독립 저장**한다.

```json
// Contract.bodyJson 예시
{
  "vi": {
    "html": "<h1>HỢP ĐỒNG DỊCH VỤ</h1><p>Điều 1: Mục đích...</p>...",
    "text": "HỢP ĐỒNG DỊCH VỤ\nĐiều 1: Mục đích...\n..."
  },
  "ko": {
    "html": "<h1>서비스 계약서</h1><p>제1조: 목적...</p>...",
    "text": "서비스 계약서\n제1조: 목적...\n..."
  },
  "en": {
    "html": "<h1>SERVICE AGREEMENT</h1><p>Article 1: Purpose...</p>...",
    "text": "SERVICE AGREEMENT\nArticle 1: Purpose...\n..."
  }
}
```

- `html`: 서식 포함 원문 (에디터 출력, Word 변환 소스)
- `text`: 순수 텍스트 (검색/색인용)
- 각 언어는 독립 편집 가능 (한 언어만 수정 시 해당 언어만 업데이트)

#### Word(.docx) 다운로드

```
사용자가 "Word 다운로드" 클릭
  → CentralApi REST endpoint: GET /api/contract/{id}/download?locale=ko&format=docx
  → 서버에서 bodyJson[locale].html → docx 변환 (docx 라이브러리: `html-to-docx`)
  → 계약서 헤더/푸터 (플랫폼 로고, 계약 번호, 페이지 번호) 자동 삽입
  → Content-Disposition: attachment 로 다운로드
```

**지원 형식:**
| 형식 | 용도 |
|------|------|
| `.docx` (Word) | 인쇄용, 편집용 (오프라인 수정 후 재업로드) |
| `.pdf` | 미리보기, 아카이브용 |
| 웹 미리보기 | 포털 내 HTML 렌더링 |

### 10.2 CentralApi 프로바이더 통합 아키텍처 — ✅ 구현 완료

3사 프로바이더는 `shared/einvoice/_internal/`에 **모두 구현 완료** 상태다.

```
shared/einvoice/
  ├── Einvoice.service.ts         ← 메인 서비스 (generate, submit, status)
  ├── Einvoice.resolver.ts        ← GraphQL API
  └── _internal/
        ├── EinvoiceProvider.interface.ts   ← Provider 공통 인터페이스
        ├── providerRegistry.ts            ← 프로바이더 선택/failover
        ├── EinvoiceConsolidator.ts        ← 통합 인보이스 라인 생성
        ├── KycLookup.ts                   ← 세금코드 KYC 조회
        ├── Wetax.provider.ts   + Wetax.client.ts   + wetax.serializer.ts   + wetax.merger.ts    ← ✅ WeTax
        ├── Viettel.provider.ts + Viettel.client.ts + viettel.serializer.ts                      ← ✅ Viettel
        └── Misa.provider.ts   + Misa.client.ts    + misa.serializer.ts                         ← ✅ MISA
```

각 Provider 구현:
```typescript
interface EInvoiceProviderAdapter {

  createInvoice(token, invoice, lines): Promise<ProviderResponse>;

```

**남은 작업:** Sandbox 환경에서 실제 GDT 테스트 제출 → Production 크레덴셜 등록 → 운영 전환

### 10.3 프로바이더 Failover 전략

```
1차 시도: 활성 프로바이더 (예: WeTax)
  → 성공: 완료
  → 실패 (TIMEOUT / PROVIDER_DOWN):
2차 시도: failoverProviderId 가 설정된 대체 프로바이더 (예: Viettel)
  → 성공: 완료, 로그에 failover 기록
  → 실패: status = PROVIDER_ERROR, 수동 재시도 대기

모든 시도: EInvoiceSubmissionLog 에 기록
  - providerType, environment, requestJson, responseJson
  - status, errorCode, errorMessage, durationMs
```

## 12. 인보이스 발행 주기 설정 (커스텀 스케줄)

### 12.1 법적 근거

**시행령 123/2020/ND-CP 제9조** (시행령 70/2025로 개정, 2025.06.01 시행):

> 반복/정기 서비스의 인보이스 발행 시점은 **양 당사자 간 데이터 대조 완료 시점**이며, 
> 발생 월의 익월 1일 또는 **약정 기간(convention period) 종료 후 7일** 이내.
> 약정 기간은 **판매자와 구매자 간 합의**로 결정한다.

**결론: 법적으로 가능.**
- 식권 서비스는 반복/정기 서비스에 해당
- "약정 기간(convention period)"을 기업/가맹점이 설정 가능
- 단, 발행 시한은 약정 기간 종료 후 7일 이내

### 12.2 발행 주기 옵션

| 주기 | 설명 | 적용 대상 |
|------|------|----------|
| **월 1회** (기본) | 매월 1일에 전월분 통합 인보이스 생성 | 대부분 기업 |
| **격주** | 15일/말일 2회 발행 | 거래량 많은 대기업 |
| **주 1회** | 매주 월요일 전주분 발행 | 실시간 정산 필요 기업 |
| **커스텀 날짜** | 기업이 지정한 특정 일자 (예: 매월 25일) | 기업 회계 마감일 맞춤 |

### 12.3 발행 스케줄 설정

#### DB 설계

```prisma
// MealCorporate 테이블에 추가
model MealCorporate {
  // ... 기존 필드 ...
  
  // 인보이스 발행 스케줄
  invoiceScheduleType    String  @default("MONTHLY") @db.VarChar(20)
  // MONTHLY | BIWEEKLY | WEEKLY | CUSTOM
  invoiceScheduleDay     Int?    // MONTHLY: 1~28일, CUSTOM: 특정 일자
  invoiceAutoGenerate    Boolean @default(true)  // 자동 생성 여부
  invoiceAutoSubmit      Boolean @default(false) // 자동 GDT 제출 여부
  invoiceNotifyEmail     String? @db.VarChar(200) // 인보이스 알림 이메일
}

// MealMerchantEnrollment 테이블에 추가
model MealMerchantEnrollment {
  // ... 기존 필드 ...
  
  // 정산 인보이스 스케줄
  settlementInvoiceScheduleType String  @default("MONTHLY") @db.VarChar(20)
  settlementInvoiceScheduleDay  Int?
}
```

#### 자동 발행 크론 (SyncWorkers)

```
매일 09:00 KST 실행:

1. 오늘이 발행일인 기업 목록 조회
   - MONTHLY: invoiceScheduleDay == today.day
   - BIWEEKLY: today.day == 1 || today.day == 16
   - WEEKLY: today.dayOfWeek == 1 (월요일)
   - CUSTOM: invoiceScheduleDay == today.day

2. 각 기업에 대해:
   a. 전 기간 SETTLED 트랜잭션 집계
   b. EInvoice DRAFT 생성 (consolidationStrategy 적용)
   c. invoiceAutoSubmit == true → 즉시 REQUESTED → SUBMITTING
   d. invoiceAutoSubmit == false → DRAFT 상태 유지 (기업 검토 대기)
   e. invoiceNotifyEmail → 이메일 발송 (검토 요청 또는 발행 완료)
```

### 13.1 쿼리 최적화

| 대상 | 패턴 | 인덱스 |

const [data, totalCount] = await Promise.all([
