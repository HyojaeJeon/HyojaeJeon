# 웹 클라이언트 — 서버 통합 인증 설계

> **대상**: SuperAdmin Portal, CorporatePortal, BrandAdminPortal (웹 기반 프로젝트 전체)
> **서버**: SuperAdmin/CentralApi (NestJS + Fastify + Apollo Server)
> **최종 수정**: 2026-04-13
> **상태**: 구현 완료 (HttpOnly Cookie 기반)

---

## 1. 아키텍처 개요

```
┌─────────────────────┐          ┌─────────────────────┐
│   웹 클라이언트      │          │    CentralApi       │
│   (Next.js)         │          │    (NestJS+Fastify)  │
│                     │          │                     │
│  Apollo Client ─────┼──HTTP──▶│  Apollo Server      │
│  credentials:include│ Cookie   │  JwtStrategy        │
│                     │◀─Set-Cookie─│                  │
│  graphql-ws ────────┼──WS────▶│  graphql-ws         │
│  connectionParams   │ Bearer   │  서버 subscription  │
└─────────────────────┘          └─────────────────────┘
```

### 핵심 원칙
- **accessToken**: HttpOnly 쿠키에 저장. 모든 HTTP 요청에 자동 전송.
- **refreshToken**: HttpOnly 쿠키에 저장. `refreshSession` mutation 시 자동 전송.
- **클라이언트 메모리**: 사용자 정보(id, displayName, userType, corporateId)만 저장. 토큰은 저장하지 않음.
- **localStorage/sessionStorage**: 토큰 저장 금지 (XSS 방어).
- **WebSocket**: 최초 연결 시 로그인 응답의 accessToken을 `connectionParams`로 전달 (WS는 쿠키 자동 전송 불가).
- **쿠키 flush 책임 분리**: resolver/service 는 `responseCookies` 버퍼에만 쿠키를 queue 한다. GraphQL plugin 은 cookie batch metadata 만 남기고, 실제 `Set-Cookie` flush 는 Fastify `onSend` 단일 경로에서 수행한다.
- **개발환경 canonical host**: 웹/서버 개발 기본 호스트는 `localhost` 로 통일한다. `localhost` 와 `127.0.0.1` 혼용 금지.

## 2. 토큰 구조

### 2.1 Access Token (JWT)

| 항목 | 값 |
|---|---|
| 저장 위치 | HttpOnly 쿠키 (`access_token` / `__Host-access_token`) |
| 만료 시간 | 7일 (환경변수 `JWT_EXPIRES_IN`, 기본값 `'7d'`) |
| 페이로드 | `{ sub, loginId, userType, sessionId, iat, exp }` |
| 서명 키 | `JWT_SECRET` 환경변수 |
| 쿠키 속성 | `HttpOnly; SameSite=Strict; Secure; Path=/` (prod) / `HttpOnly; SameSite=Lax; Path=/` (dev localhost) |

### 2.2 Refresh Token

| 항목 | 값 |
|---|---|
| 저장 위치 | HttpOnly 쿠키 (`refresh_token` / `__Host-refresh_token`) |
| 만료 시간 | 30일 |
| 형식 | `{sessionId}.{hmacHash}` |
| 회전 | 사용 시마다 새 토큰 발급 (rotating refresh token) |
| 재사용 감지 | 이전 토큰 재사용 시 세션 전체 폐기 (`REFRESH_SESSION_REUSED`) |
| 쿠키 속성 | `HttpOnly; SameSite=Strict; Secure; Path=/` (prod) / `HttpOnly; SameSite=Lax; Path=/` (dev localhost) |

## 3. 인증 워크플로우

### 3.1 로그인

```
클라이언트                          서버
   │                               │
   │  login(loginId, password,     │
   │        userType)              │
   ├──────────GraphQL Mutation────▶│
   │                               │ 1. 사용자 검증 (bcrypt)
   │                               │ 2. JWT accessToken 생성
   │                               │ 3. refreshSession 레코드 생성
   │                               │ 4. Set-Cookie: access_token=JWT
   │                               │ 5. Set-Cookie: refresh_token=RT
   │◀──── { accessToken, user } ───│
   │                               │
   │ applyAuthPayload(user)        │
   │ → 메모리에 사용자 정보 저장    │
   │ → Redux에 user/hydrated 동기화│
   │ → WS connectionParams용       │
   │   accessToken 메모리 보관      │
```

### 3.2 인증된 요청 (HTTP)

```
클라이언트                          서버
   │                               │
   │  GraphQL Query/Mutation       │
   │  (credentials: 'include')     │
   ├──────── + Cookie 자동 전송 ──▶│
   │  Cookie: access_token=JWT     │ 1. JwtStrategy: 쿠키에서 JWT 추출
   │                               │ 2. JWT 서명 + 만료 검증
   │                               │ 3. sessionId 유효성 확인
   │                               │ 4. req.user에 payload 주입
   │◀──────── 응답 ────────────────│
```

### 3.3 인증된 요청 (WebSocket)

```
클라이언트                          서버
   │                               │
   │  WS 연결 요청                 │
   │  connectionParams: {          │
   │    authorization: Bearer JWT  │
   │  }                            │
   ├──────── WebSocket ───────────▶│
   │                               │ 1. connectionParams에서 토큰 추출
   │                               │ 2. JWT 검증
   │                               │ 3. 연결 승인
   │◀──────── 연결 확립 ──────────│
   │                               │
   │  subscription { ... }         │
   ├──────────────────────────────▶│
```

### 3.4 토큰 갱신 (Silent Refresh)

```
클라이언트                          서버
   │                               │
   │  [세션 만료 2분 전 자동 실행]  │
   │                               │
   │  refreshSession mutation      │
   │  (credentials: 'include')     │
   ├──────── + Cookie 자동 전송 ──▶│
   │  Cookie: refresh_token=RT     │ 1. refresh token 유효성 확인
   │                               │ 2. 세션 회전 (새 RT 발급)
   │                               │ 3. 새 JWT accessToken 생성
   │                               │ 4. Set-Cookie: access_token=NEW_JWT
   │                               │ 5. Set-Cookie: refresh_token=NEW_RT
   │◀──── { accessToken, user } ───│
   │                               │
   │ applyAuthPayload(user)        │
   │ → 사용자 정보 갱신             │
   │ → 다음 갱신 스케줄링           │
```

### 3.5 페이지 새로고침 (Session Bootstrap)

```
클라이언트                          서버
   │                               │
   │  [메모리 세션 소멸]            │
   │  [쿠키는 브라우저가 보관]      │
   │                               │
   │  AuthBootstrap 마운트          │
   │  → bootstrapSession()         │
   │  → refreshSession mutation    │
   ├──────── + Cookie 자동 전송 ──▶│
   │                               │ 쿠키 유효 → 새 토큰 + 사용자 정보
   │◀──── { accessToken, user } ───│
   │                               │
   │ syncRedux(user, permissions)  │
   │ markHydrated()                │
   │ → 페이지 정상 렌더링          │
```

### 3.6 로그아웃

```
클라이언트                          서버
   │                               │
   │  logout mutation              │
   ├──────────────────────────────▶│
   │                               │ 1. 세션 레코드 revoke
   │                               │ 2. Set-Cookie: access_token=; Max-Age=0
   │                               │ 3. Set-Cookie: refresh_token=; Max-Age=0
   │◀──── { success: true } ───────│
   │                               │
   │ clearAccessSession()          │
   │ → 메모리/Redux 초기화          │
   │ → /login 리다이렉트           │
```

## 4. 에러 처리 및 서버 장애 대응

### 4.1 에러 분류

| 에러 유형 | 에러 코드 | 동작 |
|---|---|---|
| **인증 에러** | `UNAUTHENTICATED`, `SESSION_REVOKED`, `REFRESH_SESSION_EXPIRED`, `INVALID_REFRESH_SESSION`, `REFRESH_SESSION_REUSED`, `ACCOUNT_INACTIVE` | 즉시 로그아웃 + /login 리다이렉트 |
| **서버 에러** | 네트워크 실패, HTTP 5xx, `INTERNAL_ERROR` | 세션 유지, 30초 후 재시도 |
| **권한 에러** | `PERMISSION_DENIED`, `FORBIDDEN` | 세션 유지, 화면에 에러 표시 |

### 4.2 Apollo Client Error Link 동작

```
GraphQL 에러 수신
  │
  ├─ code === UNAUTHENTICATED / SESSION_REVOKED ?
  │   ├─ 세션 operation (login/refresh/logout) → 즉시 로그아웃
  │   └─ 일반 operation → refreshSession() 호출
  │       ├─ 성공 → 원래 요청 자동 재시도 (쿠키 갱신됨)
  │       └─ 실패
  │           ├─ 인증 에러 → 로그아웃
  │           └─ 서버 에러 → 원래 에러 전파 (로그아웃 안 함)
  │
  ├─ 네트워크 에러 → console.error (로그아웃 안 함)
  │
  └─ 기타 에러 → 화면에 에러 표시
```

### 4.3 AppShell 가드

```
hydrated 완료
  │
  ├─ Redux user 있음 → 정상 렌더링
  ├─ Redux user 없음 + 메모리 세션 있음 → 정상 렌더링 (Redux 동기화 대기)
  └─ Redux user 없음 + 메모리 세션 없음 → /login 리다이렉트
```

## 5. 쿠키 보안 설정

### 5.1 프로덕션

| 속성 | access_token | refresh_token |
|---|---|---|
| Name | `__Host-access_token` | `__Host-refresh_token` |
| HttpOnly | Yes | Yes |
| Secure | Yes | Yes |
| SameSite | Strict | Strict |
| Path | / | / |
| Domain | (없음 — `__Host-` prefix) | (없음) |

### 5.2 개발환경

| 속성 | access_token | refresh_token |
|---|---|---|
| Name | `access_token` | `refresh_token` |
| HttpOnly | Yes | Yes |
| Secure | No | No |
| SameSite | Lax | Lax |
| Path | / | / |

> `localhost:3001 → localhost:4000` 은 same-site(cross-port) 이므로 개발환경은 `SameSite=Lax` 로 충분하다.
> 로컬 개발에서는 `Secure` 를 강제하지 않아 브라우저, curl, 테스트 자동화에서 동일한 cookie 동작을 확보한다.
> 개발환경에서는 포털/서버/브라우저 테스트 모두 `localhost` 기준으로 맞춘다. host-only 쿠키와 CORS 안정성을 위해 `127.0.0.1` 과 섞지 않는다.

## 6. 서버 JWT 추출 우선순위

`JwtStrategy` (Passport)의 토큰 추출 순서:

1. **HttpOnly 쿠키** (`access_token` / `__Host-access_token`) — 일반 웹 요청
2. **Authorization Bearer 헤더** — WS connectionParams, REST API 클라이언트, 외부 시스템

이 순서로 두 경로를 모두 지원하므로, 웹 클라이언트(쿠키)와 API 클라이언트(헤더) 모두 인증할 수 있다.

## 9. 다국어 에러 메시지

서버는 클라이언트의 `Accept-Language` 헤더를 기반으로 에러 메시지를 해당 언어로 반환한다.

```
클라이언트 요청 헤더: Accept-Language: ko
서버 DomainExceptionFilter:
  1. context.locale = resolveLocale({ acceptLanguage: 'ko' })
  2. message = i18n.message({ code: 'INVALID_CREDENTIALS', locale: 'ko' })
  3. 응답: { error: { code: 'INVALID_CREDENTIALS', message: '로그인 정보가 올바르지 않습니다' } }
```

지원 언어: `ko` (한국어), `en` (영어), `vi` (베트남어)

## 10. Cloudflare 전환 시 변경 사항

현재 설계는 쿠키 기반이므로 인프라 전환(Cloudflare Workers 등)에도 인증 로직 변경이 최소화된다.

| 항목 | 현재 | Cloudflare 전환 후 |
|---|---|---|
| 쿠키 설정 | Fastify `Set-Cookie` 헤더 | Workers `Set-Cookie` 헤더 (동일) |
| JWT 검증 | NestJS Passport | Workers에서 직접 `jose` 라이브러리 |
| 쿠키 속성 | `__Host-` prefix + Secure | 동일 (HTTPS 기본) |
| CORS | Fastify enableCors | Workers CORS 미들웨어 |

## 부록: SuperAdmin 바이패스 로그인

CorporatePortal에서 SuperAdmin 계정으로 로그인하면:
1. `validateUser()`에서 `CORPORATE_ADMIN` scope 없음 → SuperAdminUser 테이블에서 fallback 조회
2. SuperAdminUser 인증 성공 → `effectiveUserType = 'SUPER_ADMIN'`
3. 같은 loginId의 CorporateAdminUser가 있으면 `corporateId`를 주입
4. 응답의 `userType`은 `SUPER_ADMIN`, `corporateId`는 연결된 기업 ID
