# Claude Code 실행 프롬프트

아래 내용을 Claude Code에 그대로 전달해서 화면 문서 전체를 표준 템플릿으로 정리하고, 이후 구현 작업으로 이어가면 된다.

```text
작업 대상:
/Users/hyojae/projects/Platform/1.Docs/기획 및 설계/프로젝트 통합설계/화면리스트/화면설계,구조,요소

목표:
각 화면 문서를 `00-화면문서-표준-템플릿.md` 형식으로 재구성하고, `BrandPosApp/PosUi` 구현에 필요한 하위 명세를 완성한다.
문서는 화면 1개당 구현 1개를 기준으로, UI 구현, Bridge 계약, UseCase, DB, CentralApi, 테스트까지 한 문서에서 연결 가능해야 한다.

필수 규칙:
- 화면 문서는 상위층과 하위층으로 나눈다.
- 상위층에는 화면 목적, 기능 목록, UI 구조, 관련 아키텍처, DB, 혁신 문서 연결을 넣는다.
- 하위층에는 구현명세, 연동 계약, 테스트, 완료 기준을 넣는다.
- 문서에 없는 기능이나 계약은 임의로 만들지 말고 `TODO`로 남긴다.
- `shared` 경로의 재사용 UI 원본을 기준으로 화면 UI를 설계한다.
- 화면별 차이, 크기, variant, handler, query/api adapter는 props 기반으로 주입 가능해야 한다.
- 화면 컴포넌트에서 `window.cefQuery`를 직접 호출하지 않는다.
- 모든 파일 경로 표기는 현재 `BrandPosApp/PosUi` 실제 구조 기준의 `.ts` / `.tsx` 파일명만 사용한다. `.js`는 사용하지 않는다.
- 이 작업 범위는 `BrandPosApp/PosUi`만이다.
- `BrandPosApp/PosUi`는 RTK Query 기반 규칙을 따른다.
- Bridge, UseCase, DB, CentralApi 연동은 설계 문서와 기존 코드 경계를 따르되, 추측으로 채우지 않는다.
- 구현 우선순위는 P0 화면부터다.

작업 방식:
1. 화면 인벤토리와 각 화면 문서를 읽고, 문서 구조를 템플릿으로 통일한다.
2. 각 화면마다 기능 목록, UI 구성, Bridge 명령, UseCase, DB, Realtime, 테스트를 채운다.
3. 한 화면 문서가 끝나면 해당 화면의 구현 파일 목록을 정리한다.
4. 불확실한 항목은 `TODO`로 남기고, 관련 원본 문서 링크를 붙인다.
5. 템플릿을 모두 맞춘 뒤, P0 화면부터 구현 순서를 확정한다.

출력 기준:
- 수정된 문서 목록
- 남은 TODO 목록
- 화면별 구현 우선순위 목록
- 다음에 구현할 화면 1개
```
