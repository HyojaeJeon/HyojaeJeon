# Claude Code 실행 프롬프트

아래 내용을 Claude Code에 그대로 전달해서 `BrandPosApp/PosUi`의 화면 구현을 병렬로 진행한다.  
이 프롬프트는 **화면 shell 구현 전용**이다. 백엔드, Bridge, UseCase, DB, CentralApi 연동은 이 단계에서 구현하지 않는다.

```text
작업 대상:
/Users/hyojae/projects/Platform/1.Docs/기획 및 설계/프로젝트 통합설계/화면리스트/화면설계,구조,요소

목표:
100개 이상 존재하는 화면 문서를 기준으로 `BrandPosApp/PosUi`의 화면 UI를 병렬로 구현한다.
각 화면은 하나의 구현 단위이며, 화면 문서 1개를 보고 화면 1개를 구현하고 문서에 진행 기록까지 남긴다.

핵심 원칙:
- 이 단계는 화면 shell 구현만 한다.
- 공통 UI는 반드시 `BrandPosApp/PosUi/src/shared`의 재사용 컴포넌트를 먼저 사용한다.
- 화면별 차이는 props로 주입한다.
- 화면 문서에 없는 백엔드 계약, Bridge 상세 shape, UseCase 실패 규칙, DB 연동, CentralApi 연동은 구현하지 않는다.
- 필요한 경우 버튼/행동은 modal open, local state, stub handler, deferred action 수준까지만 구현한다.
- `window.cefQuery`를 화면 컴포넌트에서 직접 호출하지 않는다.
- 파일 경로는 현재 `BrandPosApp/PosUi` 실제 구조 기준의 `.ts` / `.tsx` 만 사용한다. `.js`는 사용하지 않는다.
- 한 화면 문서가 끝나면 반드시 해당 문서의 상태와 진행 기록을 갱신한다.
- 완료된 화면은 문서에 "어디까지 구현됐는지"를 분명히 남긴다.
- 구현된 shell과 문서 진행 기록이 서로 다르면 문서를 우선 정정한다.

병렬 실행 규칙:
- 여러 전문 에이전트를 동시에 사용한다.
- 각 에이전트는 서로 겹치지 않는 화면 문서 집합과 파일 집합만 담당한다.
- 같은 화면 문서나 같은 소스 파일을 두 에이전트가 동시에 수정하지 않는다.
- 화면 인벤토리 기준으로 P0부터, 그리고 도메인별로 묶어서 배치한다.
- 큰 화면군은 5~15개 단위로 나누고, 각 배치는 독립적으로 끝낸다.
- Coordinator 에이전트가 문서 분할, 파일 소유권, 완료 상태를 관리한다.
- Worker 에이전트는 구현만 한다.
- Verifier 에이전트는 문서 상태, 진행 기록, 파일 경로, 누락 여부를 점검한다.

작업 방식:
1. `00-화면리스트-전체-인벤토리.md`와 개별 화면 문서를 읽고 구현 순서를 확정한다.
2. 화면별로 필요한 `shared` 컴포넌트를 확인한 뒤, 없으면 먼저 추가한다.
3. 화면 shell을 구현한다.
4. UI 상호작용은 로컬 상태와 모달 수준까지 허용한다.
5. 기능 계약이 아직 확정되지 않은 동작은 `TODO` 또는 `deferred`로 남긴다.
6. 화면 구현이 끝나면 문서의 `## 0. 문서 정보`, `## 8. 작업 명단`, `## 9. 작업 진행 기록`을 갱신한다.
7. 각 문서의 `작업 진행 기록`에는 날짜, 범위, 상태, 완료 범위, 남은 범위, 내용을 남긴다.
8. 모든 화면 문서를 처리한 뒤, 남은 TODO와 후속 구현 대상을 정리한다.

출력 기준:
- 완료된 화면 문서 목록
- 수정된 파일 목록
- 각 문서의 진행 기록 요약
- 아직 남아 있는 TODO 목록
- 다음 배치 후보
```
